## Round 1（2026-10-24）延迟攻坚落地 + F1 真正可用

提交：`5ec9e73`（26 文件 +4335/-62）

### 一、F1 从「抢不到」到「一定能用」

**实测事实**：本机 `globalShortcut.register('F1')` 恒返回 `false` —— F1 被会话外程序以 RegisterHotKey 独占（嫌疑：QQ网吧客户端 / Pubwin OL，二者常驻；旧版朗读女已不在运行）。RegisterHotKey 是独占 API，**任何重试都不可能抢到**，所以「引导退出 + 自动重试」只能解决「别的程序是旧版朗读女且用户愿意退出」这一种情况。

**方案**：新增 `src/main/platform/keyboardHook.js`，用 koffi（3.3.3，MIT，N-API 跨 ABI）安装 `WH_KEYBOARD_LL` 低级键盘钩子旁路捕获。

| 设计约束 | 做法 |
|---|---|
| 绝不吞事件 | 一律 `CallNextHookEx` 放行；只比对 `vkCode`，不做任何键盘内容记录 |
| 回调极轻 | 低级钩子 300ms 超时会被系统静默摘除 → 回调只做时间戳去重 + `setImmediate` 派发 |
| 可缺省 | koffi 缺失/非 Windows → `isSupported()=false`，退回原有冲突播报 + 5s 重试 |

**实测证据**（`scripts/tmp_probe_kb_hook.js`，keybd_event 注入真实系统输入）：

```
globalShortcutF1: false      ← 官方 API 确实抢不到
hookStart: true, backend: koffi
injected: 3 → hits: 3        ← vkCode=112 (0xF1→F1) 全命中
verdict: PASS
```

**三层保障**（hotkeyTray）：官方 API → 钩子旁路 → 冲突播报+重试。官方 API 恢复后**立刻卸钩子**（否则一次按键读两遍）。冲突播报文案按 `hooked` 分流：钩子生效时播「已自动改用底层监听，照样能朗读」，不会误报「朗读暂不可用」。

**副作用与观察**：装 koffi 后 `zoomController` 的 koffi 滚轮钩子也随之启用（`[zoom] 输入后端: backend=koffi trigger=koffi`）——这是原设计意图（可吞滚轮），但此前从未真机验证过，纳入 Phase 2 回归项。

### 二、划词抓取：771ms → 62ms（P95）

`platform/captureHost.js` 常驻 PowerShell 抓取宿主（与 sapiHost 完全解耦，仅 `WScript.Shell` + `Get-Clipboard`）。

| 路径 | n | p50 | p95 | 备注 |
|---|---|---|---|---|
| 宿主（全部） | 10 | 17 | **62** | via=host 命中 10/10 |
| 宿主稳态（剔除首次） | 9 | 17 | **33** | |
| 一次性兜底（对照） | 3 | 746 | **771** | 本机 PS 冷启动 658~950ms |
| 真实入口 readSelection | 3 | 16 | **46** | 含备份/还原 |

- 预热 `initCaptureHost()` 冷启动 863~1375ms，幂等（第二次 0ms）；**已接入 index.js，不 await**
- 语义红线守住：无选区 → `NO_SELECTION`，`stale=false`，旧剪贴板原样保留；`restored=true`
- 自动重建与兜底均实测：kill 宿主后下次抓取自愈（pid 变更）；宿主不可用 → `via=oneshot`

### 三、引擎链路：预热做了，但在线链路有硬下限

- Edge 预热真实化（首次即合成 2 字短句丢弃）+ 4 分钟保活 + `powerMonitor.unlock` 补位
- `refreshEngines()` 对可用本地引擎补 warmup；音色兜底链 云希→晓晓（回退必带 `degraded + fallbackReason`）
- AudioContext 建窗预热（首次 cue 不再付 context 创建）

**关键结论（改变了技术判断）**：Edge 单次调用理论下限 ≈ **0.87s TLS 握手 + 0.3s 服务端 TTFB ≈ 1.2s**。`node-edge-tts` 每次 `streamAudio` 新建 WebSocket 且 `turn.end` 后关闭，TLS 会话不复用（实测 `reused=false`，关证书校验仍 907ms）。**保活只能省掉模块加载+DNS 约 0.24s，摊薄不了握手**。另实测该出口 4~8 次/分钟即触发 429。

### 四、端到端延迟实测（`scripts/probe-latency.js`，新增）

口径：触发 → 反馈音 → 首句合成 → 首声（真实解码+排音，不等播完）；抓取按 WL1 实测 62ms 计入。

| 指标 | 目标 | 在线实测（3 轮） | 判定 |
|---|---|---|---|
| 反馈音 P95 | ≤200ms | **1ms** | ✅ |
| 首句合成 P50 / P95 | — | 1324 / 2094ms | — |
| 端到端 P50 / P95 | 在线 ≤1000ms | 1397 / 2169ms | ❌ |
| 播放启动 P95 | — | 6ms | ✅（不是瓶颈） |

**结论**：在线链路**不可能**达标，本地引擎是唯一根治路径 —— 这直接决定 NVSA 一键部署从「音质升级」升格为「延迟必需项」。

度量方法学修正：首版把 cue 与 synthesize 并发，cue 被抢占到 737ms（失真）；真实链路是「先播提示音再抓取/合成」，改串行后 cue=1ms。

## Round 1.6（2026-10-24）系统语音兜底：延迟达标的关键一跳

提交：`c75bf41`

### 一、发现

在等 142MB 语音包下载时顺手测了「系统自带的 Microsoft Huihui 能不能当本地引擎」：

| 项 | 实测 |
|---|---|
| 走常驻 sapiHost 通道合成 | **18 / 23 / 43 ms**（3 轮） |
| 首次预热 | 547 ms（一次性） |
| 输出 | 181424 字节 WAV |

**它比 NVSA 神经语音还快**（后者要跑模型）。而它一直被 `pickSapiVoices` 的音色白名单挡在门外——`SAPI_VOICES` 只定义了晓晓/云希，系统语音直接被丢弃 → 本地引擎判「未注册」→ 被迫走 Edge 1.4~2.2s。

**这才是「按 F1 读得太慢」的真正主因**，而且不用等 142MB 语音包就能解决。

### 二、改动（四层，缺一层就漏）

1. `voiceCatalog`：新增 `system` 兜底音色（`fallbackOnly`，不参与主循环）；NVSA 未装时退到系统中文语音，返回 `kind:'system'` 标明来源
2. `sapiBackend.probe`：有系统语音即 `available:true`，并带 `kind` + `notice` —— **不许静默降级**，上层必须能说清「现在用的是系统语音」
3. `ttsBridge`：`_engineState` 透传 `notice`/`localKind`；`sapi` 且 `kind=system` 时 label 改「系统内置语音（离线兜底）」、detail 说明「音质一般但几乎无延迟」
4. `sapiHost`：采样率改从 **WAV 头**解析。原用 `$synth.Voice.AudioFormat`，在 Huihui 上取不到值 → `sampleRate=0` → 上层按 16000 解释实际 22050 的音频 → **播放变调**（听感上会像慢放）

### 三、实测对比

| 指标 | 在线（Edge） | 本地系统语音 | 目标 | 判定 |
|---|---|---|---|---|
| 端到端 P50 | 1397 ms | **94 ms** | — | — |
| 端到端 P95 | 2169 ms | **206 ms** | ≤300 ms | ✅ |
| 反馈音 P95 | 1 ms | 2 ms | ≤200 ms | ✅ |
| 合成 P50 | 1324 ms | **15 ms** | — | — |
| 播放启动 P95 | 6 ms | 9 ms | — | — |

`probe-latency` verdict `pass=true`。**提速 10.5 倍**。

### 四、测试适配

`test-engine-routing` 从 31 用例扩到 **37**，`PASS=37 FAIL=0`：

- §3 原「NVSA 未注册 → 本地不可用 → Edge」→ 改为「NVSA 未注册 → **系统语音兜底可用**（kind=system + notice）」
- 新增 §3b「连系统语音都没有 → 才降级 Edge」，保住原断言的真正意图（降级可感知）
- `mock-sapi-host` 新增 `MOCK_NO_ANY_VOICE`：原实现固定混入 Huihui 用于验证筛选，它现在成了兜底来源

### 五、产品取舍说明

系统语音（Huihui）是旧版拼接式 TTS，音质明显不如神经语音。这里的选择是**响应速度优先**：低视力用户按 F1 后 200ms 出声、和 2.2 秒后才出声，体验差异远大于音质差异。NVSA 装好后自动换成晓晓/云希，不需要用户做任何选择。

因此 NVSA 一键部署的定位从「延迟必需」回到「音质升级」——但它仍然值得做，且这次装成功后会立即生效（`refreshEngines` 热切）。

## Round 3.1（2026-10-24）用户真机反馈三连修

提交：`7eb0ba0`（12 文件 +1573/-20）

用户实测反馈三条，全部定位到根因后编队修复（W-FIX1/2/3 并行，文件互斥）。

### ① 按热键时「已开始朗读」和正文抢声音

**根因**：`handleRead` 里立即 `announce('start')`，而 TTS 同一刻开始合成。以前 Edge 要 2 秒，播报说完正文才来；本地引擎 150ms 就出声 → **必然撞车**。这是延迟优化的连带副作用，不是偶发。

**修法**：结果性播报改 700ms 延迟确认（新增 `startAnnounceGate.js` + `useDelayedAnnounce.js`）

- 700ms 后仍静默 → 才播「已开始朗读」，让慢链路用户知道指令没丢
- 暂停/停止/失败保持立即播报；暂停/停止时 cancel，避免「刚停就补一句」
- 编排者裁决附加：`handlePlay` 无音频时直接 return（原先会念一句而实际什么都没播）

探针 16 项全过（快路径 0 次播报 / 慢路径 710ms 补播 / 连按只播一次）。

### ② 启动黑屏→白屏闪烁

**根因**：窗口背景写死 `#0f1115`（深色），且没有 `show:false` + `ready-to-show`，创建即显示 → 先露深色底，渲染完变浅色。

## Round 5（v2.4.0）：窗口融合 + 修「叉掉窗口后全盘失效」

### 用户报的三个症状，其实是同一个 bug

用户原话：

1. 「窗口叉掉以后，从右下角菜单栏就点不开了」
2. 「悬浮球图标一直是两竖，不管点几下」
3. 「选中按热键它不会出来，就低一下，也不说一下」

**根因**：主窗口被原生 X 关闭时走的是**真销毁**（`closed` → `mainWindow = null`），
而托盘、悬浮球、热键结果的投递全都依赖 `win.webContents.send`：

| 路径 | 旧代码 | 窗口为 null 时的表现 |
|---|---|---|
| 托盘点击 / 「显示主窗口」 | `if (w) { w.show(); w.focus(); }` | 什么也不做 → **点不开** |
| 悬浮球 read / play / pause | `if (win) win.webContents.send(...)` | 指令丢弃 → **点了没反应** |
| 热键抓选区 | `if (!win \|\| win.isDestroyed()) return;` | **抓完选区才丢**，只听到提示音 |

悬浮球「一直两竖」还有第二层原因：球的状态来自 `state.playback`，由渲染层上报；
窗口销毁后没人再上报 `isPlaying=false`，球就永久停在最后一次状态（两竖 = 暂停图标）。

### 修法

**A. 关窗 = 收进托盘，不销毁**
`win.on('close')` 拦截 → `hide()`；只有 `state.quitting` 才放行（托盘「退出」/`app.quit()`）。
hide 后 webContents 存活 → 托盘能 show 回来、热键结果照常送达、状态继续同步。
首次隐藏用**托盘气泡**说明（不打断音频），只提示一次。

**B. 所有投递路径改为可感知**
- 新增 `resolveWindow()`：优先现有窗口，真销毁时 `ensureWindow()` 重建；
- 托盘点击与「显示主窗口」统一走 `showMainWindow()`；
- 热键：抓选区**前**先确认有接收方（没窗口就不白抓一次），抓完再取一次（几百毫秒内可能被关）；
- 悬浮球：无接收方时语音播报，并记录 `delivered=`。

**C. 防御**：`closed` 里复位 `state.playback` 并 `broadcastState()`，防止球卡在播放态。

**D. 调试版 / 安装版 userData 隔离（用户误判的根源）**
原两者共用 `%APPDATA%\LangduNvNeo` → 探针改的主题/字号/热键会立刻串到用户的安装版；
两个进程同跑还会抢同一个朗读热键、出现两个托盘图标和两个悬浮球。
改为打包版 `LangduNvNeo`、未打包版 `LangduNvNeo-dev`，老用户设置零迁移。
