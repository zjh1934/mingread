# 放大镜方案调研 · 覆盖层 vs Windows Magnification API

> 调研 agent：W-MAG｜2026-10-24｜只调研、未改动任何产品代码（`zoomController.js` / `zoom-overlay.html` / `zoomPreload.js` 均为只读）
> 触发：用户「按住 Alt + 滚轮后先进一个程序的开始渲染页，然后鼠标周围嵌套很多很多方形的线……这种解决方案是不对的，应该去扒一下开源项目，把他们那一套直接搬过来用」
> 结论：**用户判断正确。现有方案不是"参数没调好"，是架构选错。** 应整体迁移到 Windows Magnification API（`Magnification.dll`），koffi 可以直接调，且不需要管理员权限。

---

## 0. 结论先行

| 问题 | 判断 |
|---|---|
| 「开始渲染页」根因 | 覆盖层窗口 `showInactive()` 早于内容就绪，且**每次**激活都重新走 `desktopCapturer.getSources → getUserMedia → video 首帧`（0.5~1.5s），期间整屏被 `#wait` 半透明遮罩 + 黑底覆盖 → 视觉上等于"一个程序正在启动" |
| 「嵌套方形线条」根因 | 四层叠加：`#focus` 三重叠边方框 + `#cross-v/h` 全屏十字 + `#ring` 视口边框 + **`image-rendering:pixelated` 放大后的像素块被 `feConvolveMatrix`/`feMorphology` 勾勒出网格**。最后一层是"对放大位图做边缘检测"的必然结果，**调参无效** |
| 换 Magnification API 能否根治 | **能，且是同一刀切掉两个病**：没有 HTML 页（无启动页）、没有位图二次处理（无方线）、没有抓屏链路（进入延迟 ≈ 一次函数调用） |
| `MagSetWindowSource` 的 hwnd | 是**宿主侧"放大镜控件窗口"**（类名 `WC_MAGNIFIER` 的子窗口），`rect` 是**桌面坐标下要放大的屏幕区域**。不是"取源窗口"。必须自建宿主窗口 |
| 宿主能否鼠标穿透 | **能，官方示例就这么写**：`WS_EX_LAYERED | WS_EX_TRANSPARENT` + `SetLayeredWindowAttributes(...,255,LWA_ALPHA)` |
| 推荐路线 | 主方案 = 自建全屏宿主 + `WC_MAGNIFIER` 子窗口 + 光标不动点；阶段 0 先用 `MagSetFullscreenTransform`（约 20 行）冒烟验证 |
| 旧方案去留 | 代码保留一个版本周期，降级为 `zoomBackend='overlay'` 兜底开关，**默认走新后端**；不要双默认 |

## 1. 根因定位（带行号证据）

### 1.1 现象①「先进一个程序的开始渲染页」

现有链路是**三段串行**，任何一段没到位，用户看到的就是"未渲染完的窗口"：

```
activate()  →  ensureOverlay()（首次才创建）→  loadFile(异步)
            →  showInactive()  ← 这一步就开始显示了，页面还没加载完
            →  sendActivate  →  preload: zoom:getSource
            →  主进程 desktopCapturer.getSources()   (~200~600ms)
            →  getUserMedia(chromeMediaSource)       (~300~900ms)
            →  video 首帧到位                        →  画面才出现
```

证据：

| 位置 | 内容 |
|---|---|
| `zoomController.js:168` | `overlay.loadFile(...)` 异步，不 await |
| `zoomController.js:329` | `if (!win.isVisible()) win.showInactive();` —— 加载未完成就 show |
| `zoomController.js:175-178` | `did-finish-load` 之后才置 `overlayReady`，此时才补发 activate |
| `zoom-overlay.html:48-53` | `#wait`：`position:fixed; inset:0; z-index:20` 的**整屏**深色遮罩 + 转圈 + "正在捕获屏幕…" |
| `zoom-overlay.html:9` | `html,body{ background:#000 }` —— 遮罩之下就是纯黑 |
| `zoomController.js:343-349` + `zoom-overlay.html:291-299` | `deactivate()` 停流；下次激活必须重新 `getSources + getUserMedia` → **每次都重演，不是只有第一次** |
| `scripts/alpha_probe_zoom.txt` ① | 「唤起后 450ms: active=true zoom=2.000 **fps=0**」——450ms 时仍无任何帧 |

所以用户看到的"开始渲染页"= 黑底 + 整屏半透明遮罩 + 转圈 + 边框，持续约 0.5~1.5s。**这是架构决定的，不是加个 `ready-to-show` 就能消掉的**——只要还在"抓屏再播放"，就必然有一段"有窗口没画面"的空窗。

### 1.2 现象②「鼠标周围很多很多方形的线」

按贡献从大到小，四层叠加（全部在 `zoom-overlay.html`）：

**第 1 层：`#focus` 本身就是三圈同心方框**（`zoom-overlay.html:34-39`，逻辑 `:199-209`）

```css
#focus{ border:3px solid #ffff00;            /* 亮黄框 */
        box-shadow: 0 0 0 2px rgba(0,0,0,.9),  /* 外圈黑框 */
                    inset 0 0 0 2px rgba(0,0,0,.6); } /* 内圈黑框 */
```
`zoomFocusRing` 默认 `true`（`zoomController.js:47`），边长取 `min(W,H)*0.12`。**一个光标就是 3 圈方框**。截图 `deliverables/qa-v26-zoom-8x-plain.png`（滤镜全关）里依然清晰可见——证明这一层与滤镜无关。

**第 2 层：`#cross-v` / `#cross-h` 全屏十字**（`:26-32`，`:190-198`）
2px 黄线 + 1px 黑外描边，贯穿整屏并在光标处相交，与第 1 层组合成"田字格 + 套框"的视觉结构。

**第 3 层：`#ring` 视口边框**（`:20-24`）
`position:fixed; inset:0` + `border:4px solid #ffff00` + `inset box-shadow 2px`。因为默认 `box-sizing:content-box`，4px 边框画在视口外侧被裁掉一半，只剩"内侧半条黄 + 内侧黑阴影"——屏边因此还有一圈框，与内部框形成**嵌套**关系。截图 `qa-v26-zoom-8x-plain.png` 顶部/右侧的粗黄条就是它。

**第 4 层（真正的"很多很多细方线"）：边缘增强 SVG 滤镜打在 pixelated 放大的位图上**

```css
#screen{ image-rendering: pixelated; }   /* :17 ，JS 在 :218 还会再设一次 */
```
8x 时，1 个源像素 = 64x64 的硬边色块。然后：

| 位置 | 逻辑 |
|---|---|
| `:158` | `zoom>1.02 && (edgeEnhance>0.01 || outline>0.01)` → 挂 `url(#ldnEdge)` |
| `:170-174` | 锐化核 `0 -k 0 / -k 1+4k -k / 0 -k 0`，`k = edgeEnhance*1.2`；默认 `edgeEnhance=0.30`（`zoomController.js:41`）→ k≈0.36，中心 2.44、四邻 -0.36 |
| `:175-179` | `feMorphology dilate radius=outline*3` + `feComposite operator="out"` → 沿**每一条对比边界**生成描边带，再 `feFlood` 染黄 |

对一张"已经被放成硬边色块"的位图做拉普拉斯锐化，每个色块边界都会产生过冲/振铃 → **一整片网格状细线**；`outline>0` 时 `dilate` 直接给每一块像素描黄框（`qa-v26-zoom-filter-D.png` 可见沿边缘的珠串状描边伪影；`qa-v26-zoom-8x.png` 可见黄框/黑框/斜向描边叠加）。

**附带缺陷**：`:74` 的 `x="0" y="0" width="100%" height="100%"` 未声明 `filterUnits`，默认 `objectBoundingBox` → 滤镜区域恰好等于元素 bbox，卷积/膨胀在区域边界被裁切，边缘会出现不连续跳变。

> **关键判断**：第 4 层不是"参数没调好"。只要渲染路径是"把位图放大 → 再做形态学边缘检测"，8x 上就必然出现方块阵列；`pixelated` 与锐化互相放大这个效应。**这条路必须整体换掉，不是调 `zoomEdgeEnhance`。**

### 1.3 一句话总结根因

现有实现的三个病（启动页、方块线、响应慢）来自同一件事：**用 HTML 播放一张被放大的截图**。
Windows 的放大镜是**合成器直接把屏幕内容合成进窗口**——不经过"截图→解码→绘制→CSS 变换→滤镜"任何一步，所以这三个病对它不存在。

## 2. Windows Magnification API 可行性深挖

### 2.1 能力清单

| 函数 | 作用 | 最低系统 | 备注 |
|---|---|---|---|
| `MagInitialize()` | 初始化放大引擎、**注册 `WC_MAGNIFIER` 窗口类** | Vista | 必须在建控件窗口之前调用；退出配 `MagUninitialize()` |
| `MagUninitialize()` | 销毁引擎对象 | Vista | 不做会残留系统级放大状态 |
| `MagSetWindowSource(hwnd, RECT)` | 设定**宿主控件**要显示的屏幕区域 | Vista | `RECT` 是**桌面坐标**，且**按值传参** |
| `MagGetWindowSource(hwnd, RECT*)` | 读回源矩形 | Vista | |
| `MagSetWindowTransform(hwnd, MAGTRANSFORM*)` | 设 3x3 变换矩阵（缩放/平移） | Vista | 文档只示范缩放 `v[0][0]=v[1][1]=n, v[2][2]=1` |
| `MagSetWindowFilterList(hwnd, mode, n, HWND*)` | 排除/仅含指定窗口 | **Win8** | 我们自己的 HUD 窗口必须 exclude，否则会被"拍进去" |
| `MagShowSystemCursor(BOOL)` | 显隐系统光标 | **Win8** | 对**控件**无效——控件的放大光标由 `MS_SHOWMAGNIFIEDCURSOR` 样式控制 |
| `MagSetFullscreenTransform(level,x,y)` | 整桌面放大 | **Win8** | 全屏放大模式，无需宿主窗口；`level` 1.0~4096.0 |
| `MagGetFullscreenTransform(&l,&x,&y)` | 读回全屏放大状态 | Win8 | 用来检测"系统放大镜是否正开着" |
| `MagSetColorEffect(hwnd, MAGCOLOREFFECT*)` | 5x5 颜色矩阵（反色/灰度/提对比） | Vista | 替代现有 CSS `invert/grayscale/contrast`，**零伪影** |
| `MagSetInputTransform(...)` | 把放大后坐标映射回真实坐标 | Win8 | **需 UIAccess**（签名 + 装 Program Files），本方案不需要 |
| `MagSetImageScalingCallback` | 自定义缩放回调 | Vista | **Win8 起已不支持**，且要 `MAGIMAGEHEADER`，本方案不用 |

### 2.2 koffi 能不能调？能，且成本很低

`Magnification.dll` 是普通 Win32 导出 DLL（System32 自带），纯 cdecl/stdcall C 接口，无 COM、无回调（除已废弃的 image scaling）。项目已经在用 koffi 3.3.3 调 `user32.dll`，同一套机制直接复用。

需要声明的结构体只有两个：

```js
const RECT         = koffi.struct('RECT',         { left:'int32', top:'int32', right:'int32', bottom:'int32' });
const MAGTRANSFORM = koffi.struct('MAGTRANSFORM', { v:'float[9]' });   // 3x3 行主序，连续 9 float
// MAGCOLOREFFECT = { transform:'float[25]' }  —— 只在上颜色效果时需要
// MAGIMAGEHEADER 不需要（对应已废弃的回调）
```

函数声明（`BOOL` 用 `int` 而不是 `bool`，`bool` 在 koffi 里是 1 字节的 C `bool`）：

```js
const mag = koffi.load('Magnification.dll');
const MagInitialize            = mag.func('int MagInitialize()');
const MagUninitialize          = mag.func('int MagUninitialize()');
const MagSetWindowTransform    = mag.func('int MagSetWindowTransform(void *hwnd, MAGTRANSFORM *pTransform)');
const MagSetWindowSource       = mag.func('int MagSetWindowSource(void *hwnd, RECT rect)');        // RECT 按值
const MagShowSystemCursor      = mag.func('int MagShowSystemCursor(int fShow)');
const MagSetWindowFilterList   = mag.func('int MagSetWindowFilterList(void *hwnd, int mode, int count, void **hwnds)');
const MagSetFullscreenTransform= mag.func('int MagSetFullscreenTransform(float level, int xOffset, int yOffset)');
const MagGetFullscreenTransform= mag.func('int MagGetFullscreenTransform(float *level, int *xOffset, int *yOffset)');
const MagSetColorEffect        = mag.func('int MagSetColorEffect(void *hwnd, MAGCOLOREFFECT *pEffect)');
```

### 2.3 最小可执行调用序列

**路线 A：全屏放大（无窗口，最短路径，用来冒烟）**

```js
MagInitialize();
MagGetFullscreenTransform(lv, ox, oy);            // 先存旧值，退出时还原
MagSetFullscreenTransform(2.0, px, py);           // px,py = 光标物理坐标 * (1 - 1/z)
MagShowSystemCursor(1);                           // 系统光标自动跟着放大
// 退出
MagSetFullscreenTransform(1.0, 0, 0);
MagUninitialize();
```
这就是本项目要的"按住 Alt 滚轮放大"的最小闭环，**约 20 行**。它的价值是把"koffi 能否调用 Magnification.dll / 权限是否够 / 效果是否达标"这三个未知项在半天内变成已知。

**路线 B：窗口放大（正式方案，可控、可加 HUD、不与系统放大镜抢状态）**

```js
// 1) 初始化（必须在建控件窗口之前）
MagInitialize();

// 2) 宿主窗口：全屏、置顶、分层、鼠标穿透、不抢焦点
//    exStyle = WS_EX_TOPMOST|WS_EX_LAYERED|WS_EX_TRANSPARENT|WS_EX_TOOLWINDOW|WS_EX_NOACTIVATE
hwndHost = CreateWindowExW(exStyle, className, 'LensHost', WS_POPUP,
                           disp.x, disp.y, disp.w, disp.h, null, null, hInstance, null);
SetLayeredWindowAttributes(hwndHost, 0, 255, LWA_ALPHA);   // 不透明但保留分层语义

// 3) 放大镜控件：系统预注册类 WC_MAGNIFIER（字符串 "Magnifier"），子窗口铺满宿主
hwndMag = CreateWindowExW(0, 'Magnifier', null,
                          WS_CHILD | WS_VISIBLE | MS_SHOWMAGNIFIEDCURSOR,
                          0, 0, disp.w, disp.h, hwndHost, null, hInstance, null);

// 4) 缩放矩阵
const m = { v:[z,0,0, 0,z,0, 0,0,1] };
MagSetWindowTransform(hwndMag, m);

// 5) 源矩形：以光标为不动点（见 2.5 推导）
src.left   = cx - cx / z;      // = cx * (1 - 1/z)
src.top    = cy - cy / z;
src.right  = src.left + disp.w / z;
src.bottom = src.top  + disp.h / z;
MagSetWindowSource(hwndMag, src);   // ← 每帧跟随只需重调这一句

// 6) 排除自己的 HUD 窗口，避免"HUD 被拍进放大画面"
MagSetWindowFilterList(hwndMag, MW_FILTERMODE_EXCLUDE, 1, [hwndHud]);

// 7) 退出
DestroyWindow(hwndMag); DestroyWindow(hwndHost); MagUninitialize();
```

**待实测项（3 个，写进 P0 验收）**
1. koffi 传 **32 字节结构体按值**（`RECT`）在 x64 下走隐式指针，需确认 koffi 3.3.3 处理正确；失败则直接走路线 A。
2. Electron 主线程的消息泵能否稳定分发我们自建 HWND 的 `WM_PAINT/WM_NCHITTEST`（`Magnifier` 控件由系统在其 WndProc 里绘制）。项目已有 koffi 装低级钩子的先例，预期可行；不行就把宿主放到 `worker_threads` 里自建 `GetMessageW` 循环。
3. `MagSetWindowTransform` 矩阵的**平移分量**（`v[2][0]/v[2][1]`）是否被控件采纳——只影响 `centered` 跟随模式，`fixed` 模式不需要。

### 2.4 `hwnd` 到底是"取源窗口"还是"宿主窗口"？—— 宿主

官方原文（`MagSetWindowSource`）：

> **hwnd** — The magnification window.
> **rect** — The rectangle to be magnified, **in desktop coordinates**.

配套的 `Getting Started` 明确要求：

> The magnifier control must be hosted in a window created with the `WS_EX_LAYERED` extended style. **If you include the `WS_EX_TRANSPARENT` style, mouse clicks will be passed through to the underlying application**.
> The window class of the control window **must be `WC_MAGNIFIER`**.
> In most cases you will want to apply the `MS_SHOWMAGNIFIEDCURSOR` style.
> By default, magnification is applied to **all windows other than the magnification window itself**.

所以四个问题的答案：

| 问题 | 答案 |
|---|---|
| hwnd 语义 | 宿主侧的**放大镜控件窗口**（`WC_MAGNIFIER` 子窗口）。源是"整个桌面"，不是某个 HWND |
| 要不要自建宿主 | **要**。这是绕不开的成本：必须用 koffi 建两个原生窗口（宿主 + 控件） |
| 能否鼠标穿透 | **能**，`WS_EX_LAYERED|WS_EX_TRANSPARENT`，官方示例即此法 |
| 能否全屏覆盖 | **能**。而且宿主与控件窗口默认被排除在放大源之外 → **不会自拍递归**（这条比现在的覆盖层更干净，覆盖层还要靠 `setIgnoreMouseEvents` + 停流来避免拍到自己） |
| 能否放大"其他程序" | **能**，且是它的设计目的。这正好补上现有方案的短板——现有 `desktopCapturer` 拿到的是"屏幕"，理论上也含其他程序，但受 DRM/独占全屏影响同样受限（见 §5） |

### 2.5 输入一致性：为什么"光标不动点"能免掉 UIAccess

`MagSetFullscreenTransform` 的官方注释是个坑：

> Beginning with Windows 10 Creators Update (1703), you must use `MagSetInputTransform` for input to route to the magnified element.

而 `MagSetInputTransform` **需要 UIAccess**（manifest `UIAccess="true"` + 数字签名 + 装进 Program Files 安全目录），这对一个 Electron 应用是几乎不可接受的成本。

**但这条约束只对"非光标锚定"的放大成立。** 推导（全屏模式，`offset` = 放大视图左上角对应的源坐标）：

```
屏幕点 p 上显示的内容  content(p) = offset + p / z
要以光标为不动点：content(c) = c
  ⇒ offset = c (1 - 1/z)            ← 与路线 A 的 px,py 公式一致
代回：content(p) = c(1-1/z) + p/z
```

在 `p = c` 处 `content(c) = c`：**光标底下永远显示的就是光标真实位置的那个像素，而光标本身也被放大画在原位**——所见即所点，落点天然正确，不需要 input transform。

反过来，`centered`（画面中心固定）模式会让"看到的"和"点到的"错位，**在没有 UIAccess 的前提下必须禁用或明确警告**。这一条要写进产品约束：`zoomFollowMode` 的 `centered` 只在有 UIAccess 时才放开。

### 2.6 是否从根本上消除两类问题

| 现有病症 | 换成 Magnification 后 |
|---|---|
| 0.5~1.5s 的"启动页" | 消失。窗口可在应用启动时就创建好并隐藏（常驻），激活只是 `SetWindowPos(SWP_SHOWWINDOW)` + 两次 Mag 调用（微秒级） |
| 方块线/网格/黄框 | 消失。没有 CSS transform、没有 `pixelated`、没有卷积与形态学滤波；缩放由系统合成器做高质量重采样。**且 `zoomEdgeEnhance/zoomOutline` 这两个设置项应当直接下线**（它们的存在本身就是为了弥补位图放大的糊） |
| 找不到指针 | 更好。`MS_SHOWMAGNIFIEDCURSOR` 由系统把放大后的光标画进画面，不需要十字线 + 焦点框这类"补丁式"辅助（可保留为可选，但默认应关） |
| 反色/高对比 | 更好。`MagSetColorEffect` 用 5x5 矩阵，GPU 级、零伪影，替代 `invert()/grayscale()` |
| 多显示器 | 每显示器一个宿主窗口；源矩形按光标所在显示器 clamp |
| 隐私/性能 | 更好。不再需要 `desktopCapturer` + MediaStream（现在这套在任务栏录屏指示器、GPU 占用、耗电上都更贵） |

## 4. 方案对比表

| 维度 | ① 现覆盖层（getUserMedia + CSS transform） | ② **Mag 窗口放大**（宿主 + `WC_MAGNIFIER`） | ③ Mag 全屏放大（`MagSetFullscreenTransform`） | ④ DWM 缩略图（`DwmRegisterThumbnail`） | ⑤ Windows.Graphics.Capture + 自绘 |
|---|---|---|---|---|---|
| 进入延迟 | **0.5~1.5s**（窗口首帧 + 取源 + 取流 + 首帧；实测 450ms 时 `fps=0`） | **≈0**（窗口常驻，激活 2 次函数调用，<5ms） | **≈0**（1 次调用） | 低（DWM 直接合成） | 中（会话建立 + 首帧，200~600ms；仍需 picker 或授权） |
| 缩放画质/伪影 | ❌ 方块网格 + 描边伪影 + 锐化振铃（§1.2） | ✅ 系统合成重采样，无伪影 | ✅ 同左 | ⚠️ 双线性，8x 明显发糊；且只能缩略**单个顶层窗口** | ✅ 画质最好（可拿原生分辨率帧） |
| 能否跟随鼠标 | ✅（自己算 origin） | ✅（每帧重设源矩形） | ✅（重设 offset） | ⚠️ 只能跟随被缩略窗口 | ✅ |
| 鼠标穿透 | ✅ `setIgnoreMouseEvents` | ✅ `WS_EX_LAYERED|WS_EX_TRANSPARENT`（官方示例） | ✅ 无窗口，天然穿透 | ⚠️ 目的窗口需处理命中测试 | ✅（自绘窗口可控） |
| 多显示器 | ⚠️ 切屏要重建 bounds + 重新取流（会再闪一次"启动页"） | ✅ 每屏一个宿主窗口 | ⚠️ offset 需按虚拟屏左上角换算（官方有专门示例） | ⚠️ 跨屏限制多 | ✅ per-monitor 会话 |
| 实现复杂度 | 中（已有 950 行） | **中高**（koffi 建 2 个原生窗口 + 消息泵，约 400~600 行） | **极低**（约 50 行） | 低但能力不够 | **高**（N-API 原生模块 + C++/WinRT + 权限流程） |
| 许可证风险 | 无 | **无**（自研 + MIT 参考） | 无 | 无 | 无 |
| Electron 兼容性 | ✅ 原生支持 | ✅ 主进程 koffi（已有先例）；⚠️ 不能用 Electron 窗口当宿主（Chromium 自绘 surface 会盖住 GDI 子窗口） | ✅ 完全独立于 Electron | ⚠️ 目标窗口需是 DWM 合成窗口 | ⚠️ 需自写原生模块 |
| 能否放大"其他程序" | ✅（但有上述伪影） | ✅ | ✅ | ❌ 只能一个窗口，且缩略图不含任务栏/桌面 | ✅ |
| 能否做"镜片"（局部圆/方） | ✅ | ✅（`SetWindowRgn`/改窗口尺寸） | ❌ 只能整屏 | ✅ | ✅ |
| 裁决 | 淘汰（保底） | **✅ 正式方案** | **✅ 阶段 0 冒烟 + 兜底** | ❌ 否决 | ❌ 不作主选（架构同病） |

补充说明两条被否决路线的理由：

- **④ DWM 缩略图**：`DwmRegisterThumbnail` 的语义是"把**某个顶层窗口**的实时画面缩略到我的窗口里"，没有"桌面"这个 HWND，拿不到任务栏、桌面图标、多窗口叠加后的真实画面；缩放质量也不可控（无 `pixelated`/滤镜，纯双线性）。做放大镜方向不对。
- **⑤ Windows.Graphics.Capture**：画质与延迟都比 `desktopCapturer` 好，但**架构和现在一模一样**（抓帧 → 再画），"窗口先出现、画面后到"的空窗仍在，只是变短；而且要在 Electron 里落它必须写 N-API C++/WinRT 原生模块（`GraphicsCaptureItem`、`Direct3D11CaptureFramePool`、`IsCursorCaptureEnabled`），还要处理 `GraphicsCaptureSession.IsSupported` 与 picker 授权。属于"把错的路修得更好"，性价比低于换路。

## 5. 推荐方案与分阶段实施

### 5.1 推荐

**主方案 = ② Mag 窗口放大**：自建全屏宿主（`WS_EX_TOPMOST|LAYERED|TRANSPARENT|TOOLWINDOW|NOACTIVATE`）+ `WC_MAGNIFIER` 子窗口 + `MS_SHOWMAGNIFIEDCURSOR`，源矩形按"光标不动点"每帧更新。
**阶段 0 = ③ Mag 全屏放大**：不是产品形态，是**半天内把三个未知项变成已知项**的探针。

### 5.2 分阶段

**P0 · 冒烟（半天，不改产品代码）**
- 新增 `app/scripts/probe-mag.js`：`MagInitialize` → `MagSetFullscreenTransform(2, ox, oy)` → 400ms 后 4x → 800ms 后 8x → 复位 → `MagUninitialize`。
- 记录：DLL 加载是否成功、每调用耗时、是否有权限弹窗、8x 下文字观感（截图存档到 `dist/probe/`）。
- 通过标准：`magnification.dll` 可用 + 无管理员要求 + 8x 文字可读且无伪影。
- 失败预案：若 koffi/权限在此就挂，直接终止迁移，把精力转回优化现有方案的"预热"（如启动即建覆盖层 + 常驻流）。

**P1 · MVP（2~3 天）**
- 新增 `app/src/main/magController.js`，**接口与现 `zoomController` 对齐**（`activate/bump/reset/state/applySettingsPatch`），内部换成 koffi + 原生窗口；`Alt+滚轮` 钩子直接复用（`zoomController.js:642-706` 那段不用改）。
- 宿主窗口应用启动即创建并隐藏（消灭"首次创建"抖动）；`activate` = `ShowWindow` + 设 transform/source。
- 只做 `fixed` 跟随 + 整数倍率；不做平滑、不做平移、不做 HUD。
- 验收：① 无"启动页"任何一帧（录屏逐帧确认）；② 无方框/网格；③ 从按键到画面变化 <1 帧；④ 放大态下点击落点与所见一致。
- 回滚闸门：若"消息泵"这条在 2 天内打不通，切回旧后端，转 P0'（给旧方案加"启动即预热 + 常驻流"）。

**P2 · 体验补齐（3~5 天）**
- 跟随平滑：复用现有 `zoomFollowSmoothing` 语义，对源矩形做指数平滑（`zoomController.js:494-513` 的 λ 公式可原样搬）。
- 方向键平移：现有 `panX/panY` 直接加到源矩形，语义不变（`zoomController.js:427-455`）。
- 冻结（`paused`）：停止更新源矩形即可，天然"定格"，比停流省事。
- HUD：用一个小 Electron 窗口（`alwaysOnTop`）画倍率/FPS，**用 `MagSetWindowFilterList` 排除它**，否则会被拍进放大画面。
- 颜色模式：`MagSetColorEffect`（反色矩阵 / 灰度矩阵 / 提对比矩阵）。
- **下线** `zoomEdgeEnhance`、`zoomOutline`、`zoomOutlineColor`（UI 里隐藏，设置项保留字段但不再生效）；`#focus`/`#cross-*` 默认改 `off`。

**P3 · 多屏与 DPI（2~3 天）**
- 每显示器一个宿主窗口（或单窗口 + 移屏重设 bounds）；源矩形 clamp 到显示器 bounds（官方示例就是这么 clamp 到 `SM_CXSCREEN`）。
- DPI：Electron 的 `display.bounds` 是 DIP，Mag 的 rect/offset 是**物理像素** → 乘 `display.scaleFactor`；per-monitor 混合 DPI 下必须在光标进入新屏时重算。
- 退出时务必 `MagUninitialize`，并在 `app.on('before-quit')` + `process.on('exit')` 双保险（系统级状态残留是本方案最脏的失败模式）。

**P4 · 降级链**
- 启动自检：`MagInitialize` 返回 0 → 走 `overlay` 后端（现有实现），并在设置页说明"当前为兼容模式，画质与响应较慢"。
- 检测系统放大镜：`MagGetFullscreenTransform` ≠ 1.0 时不要抢全屏模式（路线 A 专用）。

### 5.3 旧方案要不要留

**要留，但降级为兜底，且只留一个版本周期。**
- 做法：`settings.zoomBackend = 'magnification' | 'overlay'`，默认 `magnification`；`zoomController.js` 不改，新增 `magController.js` 与它并列，由一个薄分发层选后端。
- 理由：唯一未被验证的硬风险是"koffi 建原生窗口 + Chromium 消息泵"，这是**唯一可能直接卡死整条路线**的点。留旧实现 = P1 失败时零成本回滚，不必阻塞发版。
- 不要做的事：两套默认都开、或在新后端里混用 CSS 滤镜"补偿"——那会把旧病带回来。

| # | 风险 | 影响 | 触发条件 | 缓解 |
|---|---|---|---|---|
| 1 | **宿主窗口消息泵**（Chromium 主线程是否分发自建 HWND 的消息） | 放大画面不刷新/黑块 → 整条路线不可用 | P1 首日 | P0 先试全屏模式（无窗口）验证 DLL；P1 先建最小宿主只画纯色，确认能收到 `WM_PAINT`；不行则宿主放 `worker_threads` 自建 `GetMessageW` 循环 |

## 9. 给决策者的一段话

用户说"这种解决方案是不对的，应该去扒开源项目把他们那一套搬过来"，这句话是对的，但要精确一点：**开源项目没有"那一套"可搬**——MIT 许可下的实现（Hazael-F、Techwolfy、fafalone）全都是几百行的 Win32 程序，核心就是**十几个 `Mag*` 函数调用**，没有一个是"Electron + 网页"路线。真正要搬的不是代码，是**渲染路径**：从"截一张图再放大它"改成"让系统合成器把屏幕按倍数合成进我的窗口"。

代价也诚实说清楚：需要在 koffi 里手搓两个原生窗口（宿主 + `WC_MAGNIFIER` 控件）和一个消息泵，这是本项目第一次"离开 Electron 的舒适区"，也是唯一的硬风险点。所以先用 `MagSetFullscreenTransform` 二十行验证到底能不能调通；能，就按 §5.2 走；不能，就认，转回去优化现有方案的预热，而不是继续在 CSS 滤镜上纠缠。
