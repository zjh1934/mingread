### A-2 七个指定字段逐个回答

#### ① themeMode

- **存在哪**：只在渲染层 `store/settingsStore.js:30`，经 zustand `persist` 落到 localStorage `langdu-neo-settings`（partialize 见 `:111-117`）。主进程 `settings.json` 里**没有** `themeMode`，只有一个从不被写入的 `theme:'auto'`（`main/settingsStore.js:45`）。
- **谁写**：`TopBar` 三态循环（`App.jsx:741` → `setSettings({themeMode})`）、`A11ySettings` 主题按钮（`SettingsDialog.jsx:154 applyTheme`）、`theme.js:523` 系统 `prefers-contrast` 联动。
- **谁读**：`main.jsx:10-14`（建主题 + 切 `dark` class）、`theme.js:413-437`、`App.jsx:47/739`、`index.html:20`（首屏骨架读 localStorage 定底色）。

#### A-01（P1）`hotkeyCue` 开关点了不生效，重启还回弹

**位置**
- `src/renderer/components/SettingsDialog.jsx:225`
  ```jsx
  onToggleCue={(next) => toggleSystemFlag('hotkeyCue', next, '热键提示音')}
  ```
- `src/main/ipc.js:120-183`（`saveSystemSettings` 的白名单里没有 `hotkeyCue`）：
  ```js
  if ('hotkey' in p) {...}
  if ('clipboardAuto' in p) {...}
  if ('readMode' in p) {...}
  if ('hoverDelayMs' in p) {...}
  if ('hoverDetail' in p) {...}
  if ('floatBallEnabled' in p) {...}
  // …… 没有 hotkeyCue 分支
  ```
- `src/main/ipc.js:66-78`（广播快照里同样没有 `hotkeyCue`）
- `src/main/hotkeyTray.js:118-124`（主进程**从磁盘**读它）：
  ```js
  if (!require('./settingsStore').getSettings().hotkeyCue) return;
  ```

**为什么是问题**
1. 渲染层 `toggleSystemFlag` 先乐观写 store，再 `saveSystemSettings({hotkeyCue:true})`；主进程返回 `{ok:true}`（因为它不认识这个键，`persist` 里没有它，直接跳过），于是界面播报「热键提示音已开启」——**假成功**。
2. 主进程判断是否出声时读的是 `settings.json`，那里永远是 `false`（默认值），所以**提示音永远不响**。
3. 渲染层 `partialize`（`store:111-117`）也没有 `hotkeyCue`，所以重启后 store 回到默认 `false`，界面又变回「关闭」。用户视角：开了 → 没用 → 过两天自己关了。
4. `store:59` 的 `if (typeof s.hotkeyCue === 'boolean') patch.hotkeyCue = s.hotkeyCue;` 是配套的死分支（快照永不含该键）。

**建议修法**（二选一，推荐 ①）
① 主进程补全契约：`ipc.js saveSystemSettings` 增加 `if ('hotkeyCue' in p) persist.hotkeyCue = !!p.hotkeyCue;`，`systemSettingsSnapshot()` 增加 `hotkeyCue: s.hotkeyCue !== false`。渲染层无需改动。
② 若确认该功能要废弃，则删掉 `HotkeySettings.jsx:89-100` 的开关与 store 里的 `hotkeyCue`，避免留一个假开关。

**验证**：打开设置 → 常用 → 打开「按热键时播放滴提示音」→ 关掉设置，选中文字按 F1 → 无「滴」声；查 `%APPDATA%/明读/settings.json`，`hotkeyCue` 不存在或为 `false`。

#### B-04（P2）「定时关闭」被下一次朗读静默取消

**关键代码**
```js
// useStreamingPlayback.js:423-427（stop 内）
if (timerRef.current) {
  clearTimeout(timerRef.current);
  timerRef.current = null;
  setTimerActive(false);
}
// :441-445（start 内）
async start(text, opts) {
  const content = ...;
  stop();          // ← 每次开始朗读都会走到这里
```

**为什么是问题**
用户设了「30 分钟后停止」，然后换章、换书、或点「重新朗读」——每次都会 `start() → stop() → 清定时器`，定时关闭被取消。UI 上只有 `Badge` 的小圆点灭掉（见 F-05，仅颜色、无文字播报），低视力用户基本不可能察觉。睡前听书场景（本功能唯一目标场景）会直接失效。

**建议修法**：`stop()` 增加参数 `stop({ keepTimer: true })`，`start()` 内调用 `stop({keepTimer:true})`；只在用户显式停止 / 定时到点 / 卸载时清计时器。

**验证**：设 1 分钟定时 → 点「重新朗读」→ 观察 `playback.timerActive`（定时按钮圆点）是否变暗；等 1 分钟看是否自动停。

### B-5 关于 `readRef` 的结论（澄清，不是问题）

`App.jsx:304-305` 每次渲染刷新 `readRef.current = handleRead`，订阅 effect 用 `readRef.current(...)` 调用 —— 这是**规避闭包旧值的正确写法**，不是缺陷。A 类订阅 effect 里其余外部值都走 `useSettings.getState()`。**未发现「捕获旧 playback」的调用点**（详见 C-4）。

#### C-01（P2）两次 `start()` 竞争：旧文本的音色/音频会串到新文本上

**关键代码**
```js
// :441
async start(text, opts) {
  const content = String(text == null ? '' : text).trim();
  if (!content) return { ok: false, error: '没有可朗读的文本' };
  stop();                                   // ① runRef+1，清空 sentences/cache
  let list = [];
  try { r = await api.splitSentences(content); ... }   // ② 在这里让出事件循环
  optsRef.current = opts || {};
  sentencesRef.current = list;              // ③ 回来后无条件覆盖
  playIndexRef.current(0, 0, true);
}
```
```js
// :280-300（pump）
const gen = runRef.current;                 // 每轮循环开头取代际
res = await api.synthesizeOne(text, optsRef.current);
if (gen !== runRef.current) continue;       // 只挡住「stop/updateOptions」造成的作废
```

**为什么是问题**
第二次 `start()` 也调 `stop()`，`runRef` 会 +1 —— 但第一次 `start()` 的 `await` 回来后**用的是最新的 `runRef`**，代际检查完全挡不住它。于是：
- 序 A 先返回：把 A 的句子表写进 `sentencesRef` 并开始播放；序 B 再返回：覆盖句子表。**用户先听到 A 的第一句（旧文本），再被切到 B**。
- 更糟的是缓存索引错位：A 的 pump 已经带着 A 的文本发出 `synthOne`，B 覆盖 `sentencesRef` 之后结果才回来，`cacheRef.set(target, url)`（`:317`）按**索引**写入 —— 同一个索引下挂的是 A 的音频、B 的文本。之后播放到该索引会放错句（口型/文字对不上）。

**触发条件**：0.6 秒内连续两次朗读请求。悬停模式下 OCR 冷却后指针微动 + 手按 F1，或剪贴板连读，都能触发。

**建议修法**：`start()` 开头取一次令牌，`await` 之后比对：
```js
const gen = ++runRef.current;   // start 自己也要开口子
...
if (gen !== runRef.current) return { ok: false, error: 'superseded' };
```
同时把 `cacheRef` 的 key 从「索引」改为「`gen:index`」或写入前再校验一次 `gen`。

**验证**：临时把 `splitSentences` 打成随机 200-800ms 延迟，连续快速触发两次不同文本的朗读，观察第一句是否是旧文本。

## E. 渲染层与主进程的语义错位

#### E-01（P3）`ReadModeSwitch` 的乐观更新 + 回滚：逻辑在，健壮性不足

**关键代码**（`components/ReadModeSwitch.jsx:93-115`）
```jsx
const save = useCallback(async (patch, sayKey, sayText, rollback) => {
  announcer.cue('press');
  setSaving(Object.keys(patch).join(','));
  useSettings.setState(patch);                    // ① 先本地生效
  try {
    const r = await bridge().saveSystemSettings?.(patch);
    if (r && r.ok === false) {
      useSettings.setState(rollback);             // ② 失败回滚
      announcer.say('readModeFail', (r && r.error) || '设置失败');
    } else if (sayText) announcer.say(sayKey, sayText);
  } catch (e) {
    useSettings.setState(rollback);               // ③ 异常回滚
  } finally { setSaving(''); }
}, []);
```

**逐点结论**
1. **主进程侧是原子的**：`ipc.js:135-148` 先算 `persist.readMode`，再 `hoverService.setMode(mode)`，最后统一 `settingsStore.saveSettings(persist)`（`:175`）。若 `setMode` 抛错会走 catch 返回 `{ok:false}` 且**未落盘**，渲染层回滚后两边一致。✅
2. **回滚值取自点击瞬间的闭包**（`{ readMode }`，`:126`）。若在 await 期间主进程广播了新的 `readMode`（多窗口/托盘操作），回滚会把广播值覆盖回旧值。当前单窗口场景概率极低。⚠️
3. **桥缺失时判成功**：`bridge().saveSystemSettings?.(patch)` 在无桥时返回 `undefined`，`r && r.ok === false` 为 false → 走「已切换到…」播报。纯浏览器调试/主进程未就绪时会**谎报成功**。⚠️
4. `saving` 只在 finally 复位，没有超时；IPC 挂死时两个按钮永久 disabled。⚠️

**建议修法**：`if (!bridge().saveSystemSettings) { rollback; 播报失败; return }`；回滚改为「回读主进程快照」而不是写回闭包值（`const s = await bridge().getSystemSettings(); useSettings.getState().applySystemSettings(s)`）。**不建议**为第 4 点加超时（IPC 是本机调用，超时反而引入新状态）。

#### E-02（P1）`hover:read` 会打断「已暂停」和「正在合成」的朗读，但**不会**覆盖编辑中的文本

**关键代码**
```jsx

offHover = api.onHoverRead?.((payload) => {
  const t = payload && payload.text ? String(payload.text).trim() : '';

```
```js

stop();   // 清 sentences / cache / 当前位置 / 定时器
```

**先回答两个明确问题**
- **会不会覆盖用户正在编辑的文本？——不会。** `handleRead`（`App.jsx:272-302`）全程只 `playback.start(content, ...)`，从不调用 `setText`；`content` 来自 IPC 载荷或 `textRef.current`，编辑器受控值 `text` 不受影响。这一点是安全的。
- **会不会打断用户手动朗读？——会，而且在两种状态下没有防护。**

**为什么是问题**
主进程的门控只有一条（`main/index.js:556`）：
```js
hoverService.init(getMainWindow, () => !!(state.playback && state.playback.isPlaying));
```
`hoverReader.js:239` 用它拦触发。而 `state.playback.isPlaying` 是渲染层 `reportPlaybackState`（`App.jsx:191-216`）上报的 `playback.isPlaying` —— 这个值在下列状态下是 **false**：

| 状态 | `isPlaying` | `hasAudio` | 悬停会不会触发 | 后果 |
| --- | --- | --- | --- | --- |
| 正在播 | true | true | 不会（被 isBusy 挡） | ✅ |
| **用户按了暂停** | false | **true** | **会** | `start()` → `stop()` → 整段句子表/缓存/当前位置被清空，改为朗读鼠标停住的那段屏幕文字。**用户丢了在书里的位置**，且没有任何提示 |
| **首句正在合成**（600~800ms） | false | false | **会** | 同上；且与 C-01 的竞态叠加 |
| 播放完毕（ended，停在末句） | false | true | 会 | 位置归零 |

另外，`isSelfPoint`（`hover/index.js:62-77`）只在指针落在**本窗口矩形内**时才拦——用户在 Word 里打字、指针恰好停在 Word 的某段文字上，会被读出来（这是悬停模式的设定，不算 bug），但**同时**会把编辑中的朗读会话清掉。

**建议修法**（顺序执行，成本很低）
1. 渲染层加一道闸：`App.jsx:452` 的 hover 回调里判断 `if (playback.hasAudio && !playback.isPlaying) { /* 暂停态：只提示不打断 */ notify('悬停朗读已跳过：当前有暂停中的朗读', 'info', {say:false}); return; }`
2. 主进程把 `isBusy` 从「isPlaying」改成「isPlaying || buffering || (hasAudio && !ended)」，即上报侧补 `buffering`（`processPlaybackReport` 已经收到 `buffering`，只是没传给 hover）。
3. 若产品希望悬停「可以接管」，至少要保留位置：`start()` 前记录 `idxRef/offsetRef`，接管后提供「回到刚才」的入口。

**验证**：读一本多章书 → 暂停 → 把鼠标停在记事本任意文字上 0.6 秒 → 观察 `Controls` 的「第 N 句」是否归零、原书位置是否丢失。

#### G-02（P2）音色只能看到前两个

**关键代码**（`VoicePicker.jsx:138`）
```jsx
const voices = (status.voices && status.voices.length ? status.voices : FALLBACK_VOICES).slice(0, 2);
```
**为什么是问题**：这是「只有晓晓/云希两个 Edge 音色」时代的硬编码（注释 `:6` 也写着「保证面板始终只有两行」）。但产品已经加了 W-VOICESRC 音色源（`VoiceSourceSettings` 能把第三方 NVSA 音色装进本机），`voiceCatalog.js` 里也已经有第三项 `sapi:system`（系统 SAPI 全量音色，数量不定）。用户辛苦装好新音色后，选择器里根本看不到——功能装上了但用不到。具体主进程实际返回几条**待确认**（取决于本机 SAPI 探测结果），但「截断」这件事是确定的。

**建议修法**：去掉 `slice(0, 2)`，改为按 `isDefault` 排序 + 全部渲染（`VoicePicker` 的行布局已经支持任意条数）；若要限高，给列表加 `maxHeight` + 滚动，而不是丢弃数据。同时 `FALLBACK_VOICES` 只应在 `voices.length === 0` 时兜底（当前写法已满足）。
