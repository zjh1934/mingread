# 悬停朗读（Hover-to-Read）调研

> 调研：W-HOVER-RESEARCH｜2026-10-25｜只读调研，未修改任何产品代码
> 对象：朗读女 Neo v2.3.0（Electron 32 / Chromium 128 / Windows）
> 已读代码：`src/main/hover/hoverReader.js`、`src/main/hover/ocrHost.js`、`src/main/hover/index.js`、`package.json`
> 证据等级：**A**=官方文档/源码；**B**=产品官方帮助/用户指南；**C**=第三方分析/社区经验；**D**=本项目实测；**E**=推断或未查证

---

## 1. 一句话结论

**值得做，但必须把「截图 + OCR」从主路径降为兜底：主路径应是 UIA TextPattern（IA2 兜底）直接取指针下的语义文本，默认按「句」朗读并高亮当前句；OCR 只服务图片、Canvas、游戏等没有可访问文本的场景。**

三个支撑判断：

1. 你们看到的 `Chrome_RenderWidgetHostHWND` + 无 TextPattern，**不是「Chromium 不支持 UIA/IA2」的证据，而是「Chromium 的无障碍树还没被激活」的典型特征**。Chromium 官方文档明确说它为了性能会等辅助技术信号才构建无障碍树；AHK 社区的做法是向 `Chrome_RenderWidgetHostHWND1` 发 `WM_GETOBJECT`（lParam=1）把它叫醒。**A/C**
2. Chromium 的 IA2 `get_offsetAtPoint` 自 2019 年就已实现；UIA 侧有 `TextPattern.RangeFromPoint` + `ExpandToEnclosingUnit` + `GetBoundingRectangles`，可以做到**字符级定位、按行/段扩展、拿到精确屏幕矩形做高亮**。这跟 OCR 是完全不同的产品体验。**A**
3. macOS 的 Hover Text / 「朗读指针下的项目」不是 OCR，而是**对指针下的 AX 元素做命中测试，元素级取文本**；它的交互范式是「修饰键/延迟 + 元素高亮 + 可调详细度」。Windows 第三方可以做到接近，但不是完全同等：UIA/IA2 依赖目标程序暴露文本，提权窗口、安全桌面、游戏/Canvas 仍需 OCR 或直接放弃。**A/B/E**

> 决策建议：先做 2–3 天的「无障碍激活探针」验证（第 7 章 Phase 0），再决定是否重写 hover 管线。**在探针结果出来之前，不要再花时间调 OCR 参数。**

### 2.2 三条共性（比单个产品更重要）

1. **都是「先命中元素，再决定读什么」，不是「先截一块屏，再猜哪里是字」。**
   - macOS Hover Text / Speak under pointer、Narrator、NVDA、SightSpeak、HoverText 全是这个路线。
   - 只有词典类取词（金山/欧路）因为目标是「词」，才愿意走 OCR/GDI Hook。

2. **触发几乎都不是「一停就读」，而是「修饰键」或「可调延迟」二选一。**
   - macOS Hover Text 默认按住 Command；Speak under pointer 有 After delay；NVDA 是显式开关；HoverText 是按住 Alt。
   - 这说明：**悬停朗读的最大风险不是「读不到」，而是「读得太容易」**。

3. **反馈一定是「视觉高亮当前单元」，不是只出声。**
   - macOS 有 Element-highlight colour；NVDA 有 visual highlight；SightSpeak 明确「outline the text being read」；Speechify/Read Aloud 逐词/逐句高亮。
   - 对低视力用户，**「现在读的是哪一块」必须可见**；只靠声音，用户无法把听觉和版面重新对齐。

### 2.3 macOS 与 Windows 的能力边界（直接回答质疑 2）

| 能力 | macOS 系统级 | Windows 第三方 | 结论 |
|---|---|---|---|
| 指针下取文本 | AX 命中测试，系统级，覆盖大多数 App | UIA/IA2，依赖目标程序实现 provider | Windows 不是「系统级保证」，是「能拿到就拿，拿不到 OCR」 |
| 元素级语义（按钮/链接/段落） | 有 | UIA 有；IA2 有角色/文本 | 可接近 |
| 字符级定位 | AX 有 range/bounds 参数化属性 | Chromium IA2 有 `offsetAtPoint`；UIA 有 `RangeFromPoint` | **可做到，且比 OCR 精确** |
| 任意像素文字（图片/Canvas/游戏） | Hover Text 是否 OCR 未查证；大概率不做 | 只能 OCR | Windows 反而可以 OCR 兜底 |
| 提权窗口 | 系统级可读 | 普通权限读不了提权窗口；需 UIAccess（签名 + 装 Program Files） | **Windows 明确弱于 macOS** |
| 安全桌面/UAC | 系统级通常可读；安全输入框可能屏蔽 AX | 不可读/不可截 | Windows 明确更弱 |
| 首次启用延迟 | 系统常驻，几乎无感 | Chromium 需激活，首次可能数百 ms–2s | Windows 需要「预热 + 缓存」 |

**结论：Windows 第三方可以做到「80% 场景接近或超过 macOS」，但不是「同等能力」。** 超过的地方是 OCR 兜底和 UIA 的字符级 range；不足的地方是提权窗口、安全桌面、非可访问应用，以及 Chromium 的首次激活延迟。

### 2.4 浏览器扩展怎么界定「要读的一段」

浏览器扩展不需要猜像素，它的边界来自 DOM：

1. **先提正文**：用 Readability 类算法或 `article/main` 选择器，去掉导航、侧栏、页脚；这决定了「读整篇」的范围。
2. **再找块**：以 `p/li/h1-h6/blockquote/td` 等块级元素为候选；用户点击/划选时，取最近的块级祖先。
3. **再切句**：对块内 `textContent` 用 `Intl.Segmenter`（sentence）或标点规则切句；中文按 `。！？`，英文保护缩写/小数点。
4. **高亮**：把当前句包进 `<span>` 或创建 `Range`，用 CSS outline/background 高亮；逐词高亮则再用 word segmenter。
5. **连续朗读**：维护一个句子队列，读完一句自动下一句；用户点击任意句可从该句开始。

**优点**：语义边界精确、可逐词、可自动滚动、可跨句跳转。  
**缺点**：只在浏览器内；iframe/Shadow DOM/Canvas/PDF 阅读器/跨域内容受限；不能读原生应用。  
**对我们的启示**：系统级 hover 用 UIA `Document` 当「DOM 替身」；如果以后做「网页连续朗读」，浏览器扩展是比 OCR 更好的补充，但它是另一个产品面，不应和 hover 混在一起。

### 2.5 屏幕阅读器怎么把「鼠标位置」映射到「可读文本」

| 屏幕阅读器 | 映射方式 | 粒度 | 触发 |
|---|---|---|---|
| **NVDA** | 指针 → `NVDAObjectFromPoint` → 该对象的 `TextInfo` → review cursor 定位到指针处 | **字符/词/行/段落** 四档（设置里的 Text unit resolution）；官方说明「支持时读周围段落，有些控件只能读行」 | 移动即读，可开关；NVDA+M |
| **Narrator** | 指针 → UIA/MSAA 元素 → 读元素名称/文本 | **元素级**；官方文档未提供文本单位设置 | 设置里开「使用鼠标阅读并与屏幕交互」；Caps+Alt+M |

**共性**：它们都是 **point → accessible object → text**，不是 **point → screenshot → OCR**。这正是本报告建议的架构方向。  
**注意**：NVDA 是 GPL-2.0，只能读思路，不能抄代码；「review cursor + text unit」这个概念可以借鉴，实现要自己写。

## 3. 技术路线对比

### 3.1 总表

| 路线 | 可行性 | 准确率 | 延迟（热/冷） | 覆盖面 | 实现复杂度 | 许可证风险 | 结论 |
|---|---|---|---|---|---|---|---|
| **UIA TextPattern** | 高。Chrome 126+ 原生 UIA 逐步上线，Chrome 138 默认；Edge/Office/WinUI/WPF/PDF 大多可用。Electron 32（Chromium 128）需实测 `UiaProvider` 是否默认开。**A** | **字符级精确**（文本来自 AX/DOM，不是像素猜测）；但依赖目标程序暴露 | 热 10–50ms；冷 0.3–2s（树构建，量级估计，需实测） | 中高：浏览器、Office、WinUI/WPF/WinForms、Explorer、PDF | 中高：COM/跨进程/缓存/超时 | 无（OS API） | **主路线** |
| **IA2（MSAA + IAccessible2）** | 高。Chromium 自 2019 起实现 `get_offsetAtPoint`；Chromium 至今完整支持 MSAA/IA2。**A** | **字符级精确**；`get_offsetAtPoint` 返回字符 offset | 热 5–30ms；冷 0.3–1s（需激活） | 中：Chromium/Electron、Firefox、部分 Qt；UWP 不走 IA2 | 高：COM/QI/线程/超时 | 无 | **兜底/字符级** |
| **OCR（Windows.Media.Ocr）** | 高，已实现 | 约 **90%**（1080p 清晰中文测试图）；12–16px 屏幕正文更低，**未查证** | 100–300ms（本项目 900×360 实测 105ms） | **全**：可见即可，图片/Canvas/游戏/视频 | 低（已有） | 无（系统组件） | **最后兜底** |
| **模拟复制（Ctrl+C）** | 中 | 100%（可选中时） | 50–150ms | 低：只有可选中文本；控制台/图片/游戏无效 | 低 | 无 | **不用于悬停**：会改选区、覆盖剪贴板、发键盘事件，用户不可预期 |

> 说明：UIA/IA2 的「冷 0.3–2s / 0.3–1s」和「模拟复制 50–150ms」都是量级估计，不是官方指标；必须用 Phase 0 探针实测。

### 3.2 UIA 在 Chromium 上到底可不可用（重点查证）

**结论：可用，但前提是「无障碍树已激活」，而且要用对 API。**

#### （1）为什么你们只拿到 `Chrome_RenderWidgetHostHWND` / Pane

Chromium 官方文档写得很清楚：

> "For performance reasons Chromium waits until it detects the presence of assistive technology before enabling full support for accessibility APIs."
> "Windows: Chrome calls NotifyWinEvent with EVENT_SYSTEM_ALERT and the custom object id of 1. If it subsequently receives a WM_GETOBJECT call for that custom object id, it assumes that assistive technology is running."

也就是说：

- Chromium **不是**默认把所有 DOM 文本暴露给 UIA/MSAA；
- 它在等一个「辅助技术存在」的信号；
- 普通 `AccessibleObjectFromPoint` / `AutomationElement.FromPoint` 不一定会发出这个自定义 object id=1 的 `WM_GETOBJECT`；
- 所以第一次命中只拿到 renderer 的宿主 Pane（`Chrome_RenderWidgetHostHWND`，ControlType.Pane），**这正是「树没开」的表现**。

AHK 社区的成熟做法也印证了这一点：

> "Chromium might not have accessibility enabled by default... We can send Chromium the signal for accessibility by sending a special message to it (WM_GETOBJECT to Chrome_RenderWidgetHostHWND1), which activates UIA and makes the content accessible."

**可操作的激活方式：**

1. 找到指针下窗口的 `Chrome_RenderWidgetHostHWND` 子窗口；
2. `SendMessage(hwnd, WM_GETOBJECT /*0x003D*/, 0, 1)`；
3. 等 100–500ms 让树构建；
4. 再调 `AccessibleObjectFromPoint` 或 `AutomationElement.FromPoint`；
5. 之后同一进程的后续查询走热路径。

或者用启动参数强制（仅对你自己能控制的进程有效，不能对用户的 Chrome 用）：

- `--force-renderer-accessibility`
- `chrome://accessibility` 手动开（仅调试）
- 原生 UIA：Chrome 126+ 逐步上线，Chrome 138 默认；Electron 32 可用 `--enable-features=UiaProvider` 验证。

> 你们注释里说「Chromium 只在进程启动时检测屏幕阅读器标志，运行中设 SPI_SETSCREENREADER 不生效」——**现象对，原因归错了**。Chromium 官方文档描述的启用信号是 `WM_GETOBJECT`，不是 `SPI_SETSCREENREADER`。这也解释了为什么 20 个采样点全空：树根本没建，不是 IA2 没有文本。

#### （2）UIA TextPattern 能做什么

Chromium 源码里，`UIA_TextPatternId` 在以下节点可用：

```cpp
case UIA_TextEditPatternId:
case UIA_TextPatternId:
  if (IsPlatformDocument() || IsTextField() || IsText())
    return &AXPlatformNodeTextProviderWin::CreateIUnknown;
```

`ITextProvider::RangeFromPoint` 的实现：

```cpp
AXPlatformNodeWin* nearest_node =
    static_cast<AXPlatformNodeWin*>(owner()->NearestLeafToPoint(point));
start = nearest_node->GetDelegate()->CreateTextPositionAt(
    nearest_node->NearestTextIndexToPoint(point));
end = start->Clone();
```

也就是说：

- `RangeFromPoint` 返回的是**指针处最近文本位置的退化 range**（空 range），这是 UIA 规范定义的；
- 必须再调 `ExpandToEnclosingUnit(TextUnit)` 把它扩成字符/词/行/段；
- `GetText(maxCount)` 取文本；
- `GetBoundingRectangles()` 取精确屏幕矩形（物理像素），可直接用于高亮；
- `GetEnclosingElement()` 取所属元素，可读角色/名称。

**UIA TextUnit 只有 Character / Format / Word / Line / Paragraph / Page / Document，没有 Sentence。**（Microsoft 文档）  
所以「句级」不是平台给的，必须自己做标点切分。这是第 4 章的核心结论之一。

#### （3）UIA 的关键坑

| 坑 | 说明 | 应对 |
|---|---|---|
| 首次调用慢/返回 Pane | 树未激活/未建完 | 激活 + 预热 + 重试；不要拿第一次结果做判断 |
| `RangeFromPoint` 返回空 range | 规范就是退化 range | 必须 `ExpandToEnclosingUnit` |
| 没有 Sentence 单位 | UIA 枚举里没有 | 本地切句（`Intl.Segmenter` + 标点规则） |
| `TextPattern2` 未实现 | Chromium 源码把 `UIA_TextPattern2Id` 列在 Not currently implemented | 不要依赖 caret range；用 TextPattern |
| 首次请求 TextPattern 触发 `kInlineTextBoxes` 模式 | 源码注释：该属性需要 inline text boxes，首次可能更慢 | 预热；把首次开销放在启动/首次悬停，不放在每次 |
| 跨进程调用可能挂起 | UIA 调用是跨进程 COM | 放到独立 worker/helper，设 300–500ms 超时，超时降级 OCR |
| 提权窗口 | UIPI 拦截 | 普通权限读不到；要 UIAccess（签名 + Program Files）或提示用户 |
| 企业策略 | `UiAutomationProviderEnabled` 可关闭原生 UIA | 回退 IA2/OCR |

#### （4）UIA 的覆盖判断

- **好**：Chrome/Edge（激活后）、Firefox（UIA）、Office（Word/Excel/PowerPoint/Outlook）、WinUI 3/WPF/WinForms、Explorer、Settings、Edge PDF、Acrobat（多数版本）、Windows Terminal（较新版本）。
- **一般**：Electron 应用（VS Code、Slack、Discord、Teams）——取决于 Electron/Chromium 版本与是否开 UIA；IA2 通常更稳。
- **差/无**：游戏、Unity/Unreal、Canvas/WebGL 内容、部分 Java Swing/AWT（需 Java Access Bridge）、部分 Qt、自绘 UI、视频画面、图片内文字。
- **不可**：提权窗口（普通权限）、安全桌面/UAC、DRM 保护内容。

### 3.3 IAccessible2（IA2）深挖

#### （1）取文本的调用链

```text
WindowFromPoint / AccessibleObjectFromPoint(x, y)
  → IAccessible
  → QueryInterface(IID_IAccessible2)        // 失败则 IServiceProvider::QueryService
  → QueryInterface(IID_IAccessibleText)
  → get_offsetAtPoint(x, y, IA2_COORDTYPE_SCREEN_RELATIVE)  // 返回字符 offset
  → get_text(start, end) / get_textAtOffset(offset, boundary, ...)
```

需要的接口：

| 接口 | 用途 | 备注 |
|---|---|---|
| `IAccessible` | `accName`、`accRole`、`accLocation`、`accHitTest` | MSAA 基础 |
| `IAccessible2` | 角色、状态、`uniqueID`、关系 | IA2 基础 |
| `IAccessibleText` | `get_offsetAtPoint`、`get_text`、`get_textAtOffset`、`get_nCharacters` | **取文本核心** |
| `IAccessibleHypertext` | 链接/嵌入对象 | 可选 |
| `IAccessible2_2` / `IAccessibleText2` | 扩展属性/range | Chromium 支持不一致，别依赖 |
| `IAccessibleComponent` | 位置/颜色 | 可选，支持不完整 |

#### （2）Chromium 的实现细节（决定了能不能用）

- **`get_offsetAtPoint` 已实现**：2019-10-08 的提交 `417c2602a2` 实现了 `IA2::get_offsetAtPoint`（SCREEN_RELATIVE）。当前源码逻辑是：`HitTestSync(x,y)` 找到命中子节点 → 若 `IsText()` → 遍历 UTF-16 文本，用 `GetInnerTextRangeBoundsRect(i, i+1)` 判断哪个字符的矩形包含该点 → 返回 offset。
- **`get_characterExtents` 仍是 `E_NOTIMPL`**：不能通过 IA2 拿每个字符的屏幕矩形。想做逐字符高亮，IA2 这条路不行；UIA 的 `GetBoundingRectangles` 才行。
- **句子边界不要指望 IA2**：IA2 规范里 sentence 是可选边界；Chromium 历史实现直接对 `IA2_TEXT_BOUNDARY_SENTENCE` 返回 `S_FALSE`。自己按标点切句更稳。
- **文本叶子节点接口有变动**：2025 年曾有「Text leaf nodes should not support IAccessible[Hyper]Text」的改动，后来被 revert。说明这条 API 表面仍在演进；生产代码要做「QI 失败就向父节点找」的兜底。

#### （3）IA2 相比 UIA 的优势/劣势

| 维度 | IA2 | UIA |
|---|---|---|
| 取字符 offset | `get_offsetAtPoint` 直接给 | `RangeFromPoint` + `ExpandToEnclosingUnit(Character)` |
| 取行/段 | `get_textAtOffset` 支持 word/line/paragraph | `ExpandToEnclosingUnit` 支持 word/line/paragraph |
| 取句子 | 不保证（Chromium 历史不支持） | **没有 Sentence 单位** |
| 高亮矩形 | **没有**（`get_characterExtents` E_NOTIMPL） | **有**（`GetBoundingRectangles`） |
| 延迟 | 同步、通常更快 | 跨进程 UIA core，首次慢 |
| 依赖 | Chromium 78+ 就有；不依赖原生 UIA | 依赖 Chromium 126+/原生 UIA 或 UIA 模拟层 |
| Node/Electron 接入 | COM，麻烦 | 有 .NET 托管 API，但 Node 仍需 helper |
| 未来性 | 维护模式，但 Chromium 仍完整支持 | 微软/Chromium 的主推方向 |

**判断：UIA 做主路线（range 矩形 + 托管 API + 现代方向），IA2 做兜底（原生 UIA 没开/Electron 旧版/需要同步低延迟时）。**

### 3.4 OCR 路线的真实水平

#### （1）已有数据

| 数据 | 条件 | 来源 |
|---|---|---|
| 900×360 区域 21 行，稳态 **105ms**，中文可读但汉字间插空格 | 本项目实测，1920×1080，zh-Hans-CN | **D** |
| zh-Hans-CN **90.206%**，单张 1080p 图 **0.262s** | Windows 11 23H2，Ryzen 9 5900X，清晰测试图 | Windrecorder 第三方 benchmark **C** |
| 区域模式默认 **1.5× 放大** 后再 OCR | PowerToys 源码 `EnhancedScale = 1.5`；Word 模式除外 | **A** |
| 中日韩按 Unicode 类别决定是否加空格 | PowerToys `OcrTextFormatter` | **A** |

#### （2）这些数据说明什么

- **105ms 是 OCR 本身**，不是端到端。加上截图、PNG 编码、PowerShell IPC、TTS 首音，用户从「停住」到「听到」大概率在 **1s 量级**。
- **90% 是清晰 1080p 图的字符准确率**，不是 12–16px 屏幕正文。小字、抗锯齿、ClearType、低对比、深色模式、背景图都会显著拉低。
- PowerToys 都要 1.5× 放大才敢 OCR，说明 **Windows OCR 对小字并不从容**；你们直接 1:1 截 900×360，等于放弃了这一层增益。
- OCR 的「行」是视觉行，不是句子；「词」是按引擎分词，中文会被拆成单字加空格。**OCR 给不了语义边界，这是架构性的，不是后处理能完全补的。**

#### （3）OCR 的典型失败场景（按严重度）

1. **多列排版**：左右两栏的视觉行共享 Y，OCR 的 reading order 可能左右交错；只按 Y 选行必串栏。
2. **图标/边框/按钮**：会被识别成「口」「日」「0」「|」「—」等怪字。
3. **代码/表格**：缩进丢失、空格被合并、竖线被识别成 `|` 或 `l`，读出来是乱码。
4. **数字/英文混排**：`1 234`、`3.14`、`v2.3.0` 可能被拆开；英文换行被 `join('')` 直接粘成 `helloworld`。
5. **低对比/深色模式/半透明背景**：字符召回下降。
6. **动态内容/视频字幕**：截图瞬间变化，读到一半内容已经变了。
7. **竖排/艺术字/手写**：基本不可用。
8. **受保护内容/DRM**：截出来是黑屏。

#### （4）准确率怎么自己测（不要再猜）

建一个 **100–200 张屏幕截图语料**：

- 场景：Chrome/Edge 网页正文、PDF、Word、Excel、代码编辑器、Windows 设置、微信/QQ 聊天、图片 PDF、视频字幕。
- 字号：12/14/16/20px；缩放 100%/150%/200%；浅色/深色。
- 每张人工标注 ground truth（只标指针附近 1–2 段）。
- 指标：**CER（字符错误率）**、**句子边界正确率**、**指针命中行正确率**、**端到端首音延迟 p50/p95**。
- 目标：正文 CER < 3%（清晰）、12px < 8%；边界正确率 > 90%；否则 OCR 不能做默认路径。

### 3.5 模拟复制（Ctrl+C）为什么不适合悬停

- 会**改变用户选区**、**覆盖剪贴板**、**发送键盘事件**；悬停是高频动作，副作用不可接受。
- 只对「可选中文本」有效；图片、Canvas、游戏、控制台无效。
- 在浏览器/Office 里，模拟 Ctrl+C 需要先点击/聚焦，可能触发页面快捷键。
- 对低视力用户，选区变化会破坏「我正在读哪里」的空间感。
- 结论：**只用于用户显式发起的「朗读所选内容」，不要用于 hover。**

### 3.6 路线结论

**推荐「语义优先、OCR 兜底」的三级管线：**

```text
指针停住
  → ① UIA TextPattern（Document/Edit/Text 节点）
       RangeFromPoint → ExpandToEnclosingUnit(Word/Line/Paragraph)
       → GetText + GetBoundingRectangles + GetEnclosingElement
  → ② 失败则 IA2
       AccessibleObjectFromPoint → IAccessible2 → IAccessibleText
       → get_offsetAtPoint → get_textAtOffset(word/line/paragraph)
  → ③ 再失败则 OCR
       小区域截图（600×220 左右）→ 1.5–2× 放大 → OCR
       → 按 X/Y 选行 → 按行距/缩进合并 → 清理 CJK 空格 → 切句
  → 统一交给「句子切分器」→ 高亮 → TTS
```

**不要在 OCR 失败后静默；也不要在 UIA 成功时还去 OCR。** 先语义、后像素，是这次架构调整的核心。

## 4. 粒度方案对比与推荐

### 4.1 六种粒度

| 方案 | 读什么 | 边界怎么定 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|---|
| **字符/词级** | 指针下的一个词/一个字符 | UIA `TextUnit_Word/Character`；IA2 `get_textAtOffset(word/char)`；OCR 按词框 | 精确、短、像词典；适合查词/术语 | 碎片化，不成句；中文词边界不稳定；朗读体验差 | 词典、语言学习、术语查看（按住修饰键触发） |
| **行级** | 指针所在视觉行 | UIA `TextUnit_Line`；OCR 行框（按 X 选列，按 Y 选行） | 与眼睛位置一致；代码/表格/表单友好；实现简单 | 视觉行 ≠ 句子；正文会被硬切断；换行处英文粘词 | 代码、终端、表格、UI 标签、PDF 表格 |
| **句级** | 包含指针位置的一个完整句子 | 从命中 offset 向前找到上一个句末标点，向后找到下一个；用 `Intl.Segmenter` + 标点规则；限制 20–60 字，硬上限 100 字 | 语义完整、长度适中、最像「读一段」；适合正文 | 需要文本 API 或可靠标点；OCR 标点错误会切错；长句要二次切分 | **网页/PDF/Word 正文的默认** |
| **段落级** | 指针所在段落 | UIA `TextUnit_Paragraph`；OCR 按行距 + 左缩进 + 空行 + 字号变化合并 | 上下文完整；适合短段落/卡片 | 太长、容易读到无关内容；低视力用户听到后面忘了前面 | 短段落、说明文字、邮件正文（需限制长度） |
| **元素级** | 指针下的一个 UI 元素（链接/按钮/菜单项/列表项/图片） | UIA `FromPoint` + `GetEnclosingElement`；IA2 `accRole/accName`；读 Name + Role | 语义稳定；能读图标按钮；不会串到相邻文本 | 一个 `<p>` 可能是一个大元素；也可能被拆成多个 span；长正文不适合 | 按钮/链接/菜单/表单/工具栏/图标 |
| **块/文章级**（补充） | 整篇正文/一个内容块 | DOM 正文提取（Read Aloud 式）；或 UIA DocumentRange | 适合连续听读；可分句排队 | 不是「悬停」粒度；需要明确的开始/停止 | 「从这里开始读整篇」而不是 hover |

### 4.2 推荐：默认「句级」，按场景切换

| 场景 | 默认粒度 | 理由 |
|---|---|---|
| 网页、PDF、Word 正文 | **句** | 语义完整，长度可控；UIA/IA2 都能扩到 line/paragraph 后再切句 |
| 代码、终端、表格 | **行** | 视觉行就是逻辑行；句读无意义；保留缩进/空格 |
| 按钮、链接、菜单、表单标签 | **元素** | 短、带角色；读「按钮：保存」比读一个词有用 |
| 图标、图片、无文本控件 | **元素（Name/Alt）**，无则 OCR | 先读可访问名称；没有名称再 OCR，避免读图标噪声 |
| 词典/语言学习 | **词**（按住修饰键） | 精确取词；不与默认句级冲突 |
| 长文连续阅读 | **句 + 继续** | 一次只读一句；按 Space/继续读下一句，避免一次读 300 字 |
| 多列排版 | **句（按列）** | 先按 X 聚类分列，再在列内切句；不要跨列合并 |
| 图片/Canvas/游戏 | **OCR 行 → 句** | 没有语义 API；只能视觉行 + 标点合并，明确告知可能不准 |

**产品默认值建议：**

- 默认粒度：**句**；
- 句长目标：**20–60 个汉字**（英文 80–160 字符）；硬上限 **100 汉字**；
- 超过上限：在最近的逗号/分号/冒号处切；没有则按 2 个视觉行切；末尾加「还有下文」的轻提示（可关）；
- 用户可在设置里选「词/行/句/段」；默认不暴露「字符」，避免噪音；
- 每个应用可覆盖（代码编辑器 → 行；浏览器 → 句；Excel → 单元格/行）。

### 4.3 句子切分怎么做（这是产品核心，不是小工具）

平台不给 Sentence，所以必须自己实现，且要处理中英混排：

1. **优先 `Intl.Segmenter`**：Electron 32 / Node 20 自带 full ICU，`new Intl.Segmenter('zh', { granularity: 'sentence' })` 可用；英文用 `'en'`。它比正则更懂缩写/省略号。
2. **中文标点兜底**：`。！？!?；;…` + 换行；`……`、`——` 不单独切；引号/括号内的句末标点不切（如「他说：“走吧。”」）。
3. **英文保护**：`Mr.`、`Dr.`、`e.g.`、`i.e.`、`vs.`、`etc.`、版本号 `2.3.0`、URL、邮箱、小数点。
4. **OCR 文本的特殊处理**：OCR 经常丢标点；如果整段没有句末标点，**不要硬切句**，退化为「行 + 下一行」直到出现标点或达到 2 行；并标记来源为 OCR（可在调试面板显示）。
5. **跨行合并**：先把同一段落的视觉行合并（行距/缩进/字号），再切句；不要在单行内切句，否则会把句子切成两半。
6. **英文换行**：合并时补空格；行末 `-` 且下一行小写 → 去连字符；不要把 `hello` + `world` 直接 `join('')`。

> 当前实现 `picked.map(l => l.t).join('')` 对中文是对的，对英文是错的；这是第 6 章的一个具体缺陷。

### 4.4 元素级也要有「读什么」的决策树

指针停在一个窗口上，不要读窗口标题；按下面顺序决策：

```text
1. 命中元素是密码框（UIA `IsPassword` / IA2 protected state）→ 不读
2. 是 Button / Link / MenuItem / Tab / CheckBox / RadioButton / ComboBox
   → 读 Name + Role（"按钮：保存"）；Name 为空则读 HelpText；再空则 OCR
3. 是 Edit / Document / Text
   → 取 offset → 句级；如果是代码/表格模式 → 行级/单元格
4. 是 Image
   → 读 Name/Alt；没有则 OCR（可选）
5. 是 TitleBar（指针在标题栏）
   → 读窗口标题（这是唯一该读标题的场景）
6. 是 Pane/Client 且没有文本
   → 不读标题；尝试 OCR；OCR 也没有 → 静默
7. 是 List/Table
   → 读当前 item/cell；表格读「列头：单元格」；不要读整表
```

**回答「停在窗口上到底读什么」：读指针下的元素，不读窗口标题；只有指针真的在标题栏上才读标题。**

## 5. 交互设计要点

### 5.1 触发：延迟 + 修饰键，二选一，不要「一停就读」

| 模式 | 规则 | 适合谁 |
|---|---|---|
| **停留触发（默认）** | 指针静止 **500–700ms**（默认 600ms），且累计移动不超过 **12–16px** 半径 | 低视力用户，手不想一直按键 |
| **修饰键触发** | 按住 Alt（或 Ctrl）才读；松开即停 | 需要精确控制/不想误触的用户 |
| **激活锁** | 三击修饰键进入「常开」，再击退出（macOS Hover Text 的做法） | 手部灵活度不足、无法持续按键 |
| **开关式** | 像 NVDA/Narrator 一样显式开/关鼠标朗读 | 屏幕阅读器用户 |

**关键修正：当前 `moveTolerancePx = 4` 太严。** 低视力用户常伴手抖/眼震；4 物理像素在 125% 缩放下只有 3.2 DIP，每 120ms 采样一次，任何轻微抖动都会把 `_stillSince` 重置，导致**永远不触发**。建议：

- 用「停留窗口内的累计位移」而不是「相邻两次采样的差值」；
- 或把容差放到 **8–12 物理像素**，并做 3 点中值滤波；
- 对 tremor 用户提供「更宽容」预设（16px / 900ms）。

### 5.2 反馈：必须让用户看见「现在读的是哪一块」

| 反馈 | 做法 | 注意 |
|---|---|---|
| **精确高亮** | UIA `GetBoundingRectangles()` 拿句子/行的屏幕矩形；画 2–3px 高对比描边 + 轻微外发光；多行句子画多个矩形 | 不要用半透明填充盖住文字；不要全屏压暗（低视力用户会迷失） |
| **当前单元标签** | 在光标右下（避让屏幕边缘）显示小胶囊：「正在朗读 · 第 2 句」 | 不要遮住正在读的文字；不要读「第一段」出声（除非用户要求） |
| **起始音** | 开始前 80ms 的轻提示音（可关） | 让用户知道「开始了」，而不是等 1s 后突然出声 |
| **角色提示** | 控件读「按钮：保存」「链接：下一步」；正文不读角色 | 只对短控件加角色，避免正文变啰嗦 |
| **失败反馈** | 连续 2–3 次没取到文字时，显示一次「这里没有可读文字」；不要每次静默 | 静默会让用户以为功能坏了 |

**为什么高亮比语音提示重要：** 低视力用户的核心问题是「视觉定位」；一句「第一段」不能告诉他屏幕上的哪一块被读了。macOS 的 Element-highlight、NVDA 的 visual highlight、SightSpeak 的 outline 都是同一个逻辑。

### 5.3 停止与切换

| 事件 | 行为 |
|---|---|
| **Esc** | 立即停止 TTS、清除队列、隐藏高亮（全局键盘钩子，需保证不吞键） |
| **单击** | 立即停止；不要触发页面点击（如果 overlay 是 click-through，点击会落到目标应用，需接受） |
| **指针移动 > 60–80px** | 停止当前朗读；若移动到新文本并停留，则切换 |
| **滚动/滚轮** | 立即停止并失效缓存；滚动后 300ms 内不触发，避免读到滚动中的内容 |
| **窗口切换/最小化** | 停止；清空当前元素引用 |
| **新悬停** | 先等 300–400ms 新停留；确认后「淡出旧句 → 读新句」，不要立刻打断造成碎片化 |
| **朗读自然结束** | 保留高亮 1.5–2s 再淡出，让用户有时间回看 |

**读到一半用户移开鼠标怎么办？**

- **默认继续读完当前句**，不要一移开就停。理由：低视力用户会不自觉地微移鼠标来追随文字；一移就停会让朗读不断被打断。
- 如果指针**离开当前文本块并停在别处** ≥ 400ms → 切换。
- 如果指针移到空白/窗口外 → 继续读完当前句，然后停。
- 提供设置「移动即停」，给需要严格控制的用户。

### 5.4 防误触

| 措施 | 建议 |
|---|---|
| **静止阈值** | 600ms 默认；可调 300–1500ms；tremor 预设 900ms |
| **移动容差** | 累计 12–16px 半径；不要用 4px 单帧差值 |
| **修饰键** | 可选「必须按住 Alt」模式；默认不强制，但提供 |
| **只在特定程序生效** | 白名单/黑名单：浏览器、PDF、Word、记事本默认开；游戏、视频播放器、远程桌面默认关 |
| **不读自己的 UI** | 指针在本应用窗口上不读；截图区域要排除自己的浮层/HUD（`setContentProtection`/`WDA_EXCLUDEFROMCAPTURE`） |
| **不读密码框** | UIA `IsPassword`；IA2 protected state；OCR 无法可靠判断，遇到密码管理器/银行类应用直接黑名单 |
| **不在拖拽/划选/输入法组合时触发** | 检测鼠标按键状态、`WM_IME_COMPOSITION`、选区非空；有选区时优先「朗读所选」而不是 hover |
| **不在内容滚动中触发** | 滚轮事件后 300ms 冷静期 |
| **不在安全桌面/UAC 触发** | 直接跳过 |
| **不读提权窗口** | 检测 UIA `E_ACCESSDENIED` 或窗口完整性级别；提示「该窗口权限较高，无法朗读」 |

### 5.5 重复悬停与边界

- **同一位置不重复读**：指针移动 < 32–40px 且内容未变 → 不重读。当前 24px 可以，但建议 32–40px，减少抖动导致的重复。
- **重读快捷键**：提供一个「重读当前块」热键（如 Alt+R），不必移开再回来。
- **内容变化要失效**：滚动、DOM 变化、窗口切换、视频帧变化 → 清缓存；不要因为指针没动就永远不重读。
- **失败可重试**：当前 `_firedPos` 在扫描前就设了，OCR 失败后必须移动 24px 才能再试；应改成「失败后 1s 允许同位置重试」。
- **读到一半被打断**：再次悬停同一处，默认从**句首**重读，而不是从打断处续读；低视力用户需要完整句子。可选「续读」。

### 5.6 低视力用户特有的取舍

1. **容忍抖动 > 追求灵敏**：宁可晚 200ms 触发，也不要因手抖永远不触发。
2. **句子 > 词**：词级对低视力用户信息量太小，频繁触发反而累；词级应是「按住修饰键」的专家模式。
3. **高亮 > 语音提示**：视觉定位是核心痛点。
4. **不要抢焦点/不要改选区**：焦点一跳，屏幕阅读器/放大镜的上下文就乱了。
5. **音频优先但可打断**：首音要快；Esc 必须立刻停。
6. **一次只读一个单元**：不要自动连读整段；用户需要时间消化。

### 6.1 三个架构级问题（比单点 bug 更重要）

1. **像素优先，而不是语义优先。**
   这套管线的所有边界都来自「OCR 行框」，所以它天然不知道句子、段落、列、控件。调参只能改善「读得准一点」，不能改善「读得对」。

2. **没有「元素」概念，所以无法回答「停在窗口上读什么」。**
   当前实现只能读「指针 Y 落在哪一行」，无法区分标题栏、按钮、正文、图标。产品上必须引入元素类型决策树（4.4）。

3. **延迟预算错配。**
   650ms 停留是为了防误触，但后面又接 105ms+ 的 OCR 和 TTS，用户感知是「停了很久才响」。语义路径可以把「取词」降到 10–50ms，把预算留给 TTS 首音和防误触。

## 7. 分阶段实施建议

### Phase 0：无障碍激活探针（2–3 天，决策门）

**目标：回答一个唯一关键问题——在目标应用里，UIA/IA2 到底能不能稳定拿到指针下的文本和矩形？**

做什么：

1. 写一个**独立探针**（C# .NET 8 控制台最省事；不要先接 Electron）：
   - 枚举指针下 HWND；
   - 如果是 Chromium，向 `Chrome_RenderWidgetHostHWND` 发 `WM_GETOBJECT(0, 1)`；
   - 等 300ms；
   - `AccessibleObjectFromPoint` → QI `IAccessible2` → QI `IAccessibleText`；
   - 调 `get_offsetAtPoint`、`get_text`、`get_textAtOffset(line/paragraph)`；
   - 同时用 UIA：`AutomationElement.FromPoint` → 向上找 Document/Edit → `TextPattern.RangeFromPoint` → `ExpandToEnclosingUnit` → `GetText` + `GetBoundingRectangles`；
   - 打印：元素角色/名称、文本、offset、矩形、耗时（冷/热）、是否成功。
2. 测 12 个目标应用：
   Chrome、Edge、Firefox、VS Code、Slack/Teams、记事本、Word、Excel、PowerPoint、Outlook、Edge PDF/Acrobat、Windows Terminal、Explorer、设置、一个 Qt/Java 应用（如有）、一个游戏/Canvas。
3. 每个应用测 20 个点（正文/标题/按钮/空白/图片/多列/代码/表格），记录成功率和延迟。

**决策门：**

- 若 ≥ 8/12 应用能稳定拿到文本 + 矩形，且热路径 p95 < 150ms → **按本报告的语义优先方案重写**。
- 若 5–7/12 → 语义优先 + OCR 兜底，但默认粒度要更保守（行级），并明确「部分应用不支持」。
- 若 < 5/12 → 保留 OCR 主路径，先修第 6 章的 1/2/4/5/6/10 号缺陷，把 OCR 体验做到「可用但有限」，不要承诺 macOS 级体验。

**Phase 0 的产出：** 一张「应用 × 能力 × 延迟」矩阵，直接决定后面的架构。**这是最该先做的事。**

### Phase 1：最小可用（1–2 周）

- 引入常驻 C# helper（UIA + IA2 + OCR 三合一），JSON over stdin/stdout，替换当前 PowerShell OCR 宿主（或至少并行）。
- 管线：UIA → IA2 → OCR；每级 300–500ms 超时；失败降级。
- 粒度：默认句级；控件元素级；代码/表格行级（先做 Chrome/Edge/Word/PDF/记事本）。
- 高亮：UIA rects 精确高亮；OCR 用行框。
- 停止：Esc、点击、移动 > 80px、滚动。
- 防误触：600ms + 12px 累计容差；不读自己窗口；不读密码框。
- 验收：Chrome/Edge/Word/PDF 正文命中率 > 90%；p95 首音 < 600ms；无卡死；不回归放大镜。

### Phase 2：体验完善（1–2 周）

- 设置：粒度（词/行/句/段）、延迟、容差、修饰键模式、激活锁、按应用规则。
- 反馈：高亮样式、当前句标签、起始音、失败提示；高亮避让光标/屏幕边缘。
- 行为：同位置不重读、重读热键、内容变化失效、失败重试、移动即停/继续读完。
- 多屏/DPI：按 DIP 定义区域；混合 DPI 测试；跨屏截图。
- 隐私：不落盘、密码框、敏感应用黑名单、浮层排除捕获。
- 验收：5 名低视力用户可用性测试；误触发 < 1 次/10 分钟；「知道现在读哪」≥ 4/5 用户能指出。

### Phase 3：覆盖与质量（持续）

- OCR 预处理：600×220 区域、1.5–2× 放大、深色模式反色、对比度增强；CJK 空格/英文换行/数字保护。
- 表格/代码模式：UIA Table/Grid → 单元格 + 列头；代码保持行/缩进。
- 应用适配：Electron（VS Code/Slack/Teams）、Java（Access Bridge）、Qt、PDF 扫描件。
- 质量体系：100–200 张语料、CER/边界/延迟回归；每次发版跑。
- 可选：浏览器扩展「网页模式」，用 DOM 做句/词级高亮和正文连续朗读（Read Aloud 路线），与系统级 hover 互补。

### 7.1 指标与目标

| 指标 | 现状（估计） | Phase 1 目标 | Phase 3 目标 |
|---|---|---|---|
| 语义取词命中率（Top 10 应用） | 未测（当前 OCR 路径） | > 85% | > 95% |
| 端到端首音 p50 / p95 | ~1.0–1.5s（估） | < 500ms / < 800ms | < 350ms / < 600ms |
| 句子边界正确率 | 未测 | > 85% | > 95% |
| OCR CER（清晰正文） | ~90% 准确率（≈10% CER） | < 5% | < 3% |
| 误触发 | 未知 | < 1 次/5 分钟 | < 1 次/10 分钟 |
| 卡死/无响应 | 未知 | 0（超时降级） | 0 |

### 7.2 风险与止损

| 风险 | 概率 | 影响 | 止损 |
|---|---|---|---|
| Electron 32 的 UIA TextPattern 不可用 | 中 | 主路线受阻 | 先用 IA2；或升级 Electron；或 OCR 兜底 |
| IA2 在 CJK/emoji 上 offset 偏移 | 中 | 边界错 | 用 UIA rects 校验；自建单测语料 |
| UIA 调用挂起 | 中 | UI 卡死 | 独立 helper + 超时 + 进程重启 |
| 企业策略关闭 UIA | 低 | 部分用户失效 | IA2/OCR 兜底；文档说明 |
| 低视力用户不喜欢句级 | 中 | 体验不符 | 提供行/段/词设置；可用性测试前置 |
| OCR 隐私/落盘 | 高 | 信任风险 | 内存流、不缓存、黑名单、隐私说明 |

### 7.3 明确不要做

- 不要做 GDI `TextOut` Hook（ legacy、对 Chromium/DirectWrite 无效、易被安全软件拦）。
- 不要在 hover 时模拟 Ctrl+C（改选区/剪贴板，副作用不可接受）。
- 不要默认每次悬停都整屏 OCR（延迟/隐私/准确率都差）。
- 不要用元素 `Name` 读长正文（可能为空/截断/重复）。
- 不要读窗口标题来回答「指针在窗口上」（只有标题栏才读）。
- 不要为了「看起来像 macOS」而强制按住修饰键；默认停留触发 + 可选修饰键更符合低视力用户。

## 8. 本机实测补充（写于本调研之后，修正第 3.2 节的推测）

调研第 3.2 节提出「Chromium 的无障碍树可能是没被激活，发 WM_GETOBJECT 即可」。
技术负责人随后做了**决定性实验**，结论如下：

### 8.1 实验设置

- 目标：本应用自身窗口（Electron 32.3.3 / Chromium 128），窗口内有大量已知文字
- 步骤：
  1. `FindWindowExW` 找到子窗口 `Chrome_RenderWidgetHostHWND`（成功，hwnd 非 0）
  2. 分别发送 `WM_GETOBJECT(0x003D)`，`lParam = 1` 与 `lParam = -25(UiaRootObjectId)`
  3. 调用 `app.setAccessibilitySupportEnabled(true)` 显式启用
  4. 等待 3 秒后，用 `AutomationElement.FromPoint` 连续查询 5 次（间隔 1.5s）

### 8.2 实验结果

```
SendMessage(WM_GETOBJECT, lParam=1)  -> 0
SendMessage(WM_GETOBJECT, lParam=-25) -> 0
element: ControlType.Pane | class=Chrome_RenderWidgetHostHWND | name=Chrome Legacy Window
textpattern: False          ← 5 次一致
```

**即使显式启用无障碍 + 主动激活 + 多次重试，`FromPoint` 仍只返回 HWND 级 Pane，没有 TextPattern。**

### 8.3 由此确定的路线

| 结论 | 依据 |
|---|---|
| **浏览器场景 UIA 不可行**（至少本版本 Chromium） | 上述 5 次查询全部只有 Pane |
| **OCR 是浏览器/PDF/图片的唯一可行取词** | 实测 zh-Hans-CN，稳态 105ms |
| **OCR 也能做高亮**：`OcrLine.Words[].BoundingRect` 给出每行/每词的矩形 | 本项目 ocrHost 已返回行级 y/h |
| **粒度必须后处理**：OCR 给的是视觉行，不是句子 | 必须按标点/`Intl.Segmenter` 重新切句 |

补充：本机 `System.Windows.Point` 需要额外加载 `WindowsBase` 程序集，否则报「找不到类型」——
这是个会浪费半天的低级坑，已记入探针注释。

### 8.4 对第 5.1 节的确认：当前实现的触发阈值确实过严

`hoverReader.js` 里 `moveTolerancePx = 4`（物理像素）+ 「相邻两次采样差值」判定，
对低视力用户（常伴手抖）几乎不可能触发。调研建议的「累计位移 + 8~12px + 中值滤波」是对的，
属于**必须修**的缺陷，不是优化项。

### 8.5 修正后的实施顺序（替代第 7 章的 Phase 0）

Phase 0 的「12 个应用 UIA 命中率测试」在本机已无必要（Chromium 已判死），改为：

1. **P1 粒度重构**：OCR 行 → 段落合并 → `Intl.Segmenter` 切句 → 读完整句（20~60 字，硬上限 100）
2. **P2 触发修正**：累计位移判定 + 容差放宽 + 手抖预设
3. **P3 视觉反馈**：用 OCR 的行矩形画高亮框（读的是哪一句，看得见）
4. **P4 边界决策树**：标题栏/按钮/正文分别怎么读；连续 2~3 次取不到文字要给一次提示
5. **P5 英文与混排**：跨行合并补空格、去连字符（当前 `join('')` 对英文是错的）
